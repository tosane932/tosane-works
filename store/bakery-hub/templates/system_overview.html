1. Bakery Hub全体の流れ

まずは、売上入力の「画面を開く → 数量を送る → 保存結果を見る」を例に、処理の役割を分けて読んでみましょう。

  1. ブラウザからリクエストGET /inputで画面を開き、フォームからPOST /inputで日付・商品ID・数量を送ります。
  2. Flaskのrouteが受け取るapp.pyのinput_sales()が担当。認証を確認し、利用者に許可されたDatasetを取得します。
  3. Pythonで入力を確かめる日付や数量を変換し、ifで不正値を拒否。forで各行を確認し、別Datasetの商品を保存対象に含めません。
  4. SQLAlchemyを通してDBへProduct・DailySalesモデルを使って読み書きします。PostgreSQLとSQLiteでは、同じ商品・日付の行があれば数量を更新します。
  5. 保存を確定してHTMLを作るdb.session.commit()で確定。失敗時はrollback()で取り消します。render_template()がデータをJinjaへ渡し、HTMLを生成します。
  6. ブラウザで表示・操作HTMLとCSSで画面を表示。JavaScriptは入力欄の操作やAIボタンなど、画面上の動きを担当します。

本番用DBはPostgreSQL、通常のpytestはSQLiteのメモリ内DBです。Dashboardやホームの予定更新などではJSONを返し、JavaScriptが画面を更新します。このシステム概要自体は、業務データを取得せず説明を表示します。

2. 1つの処理を最後まで追ってみる

題材は「売上入力 → DB保存 → Dashboard表示」。今月の登録済み商品に数量を入力する場面を、1段階ずつ開いて追いましょう。

ブラウザ操作 → HTTP → Flask / Python → SQLAlchemy → DB → Flask / Jinja → HTML → ブラウザ表示、という往復です。保存とDashboardの表示は、別々のリクエストでつながります。

  1. 売上入力画面を開く

    GET /inputで、今月の商品と今日の数量を表示します。

    処理と基礎を読む

    FlaskがURLに対応するinput_sales()を呼びます。認証とDatasetを確認し、_get_current_products()で現在のDataset・今年・今月の販売中商品をqueryします。今日の数量も読み、render_template()でinput.htmlへ渡します。Jinjaが商品を繰り返し並べたHTMLを作り、ブラウザがCSSと合わせて表示します。

    ここで学べる基礎
    Web：GET / route / response
    Database：query / 絞り込み
    Frontend：Jinja / HTML / CSS

    {{ source_links(['templates/input.html']) }}

  2. 入力して送信する

    「本日の売上個数を更新する」ボタンから、日付・商品ID・数量を送ります。

    処理と基礎を読む

    HTML formのmethod="POST"により、ブラウザがPOST /inputを送ります。CSRF tokenの確認と認証を通った後、同じinput_sales()がPOST用の分岐へ進みます。日付はrequest.form.get("date")、複数行の商品IDと数量はrequest.form.getlist()で受け取ります。

    ここで学べる基礎
    Frontend：HTML form / name
    Web：POST / request / CSRF
    Python：if / list

  3. Pythonで入力を確認する

    全行を検証し、不正な入力や別Datasetの商品を拒否します。

    処理と基礎を読む

    日付をdatetime.date.fromisoformat()で変換し、商品ID・数量の件数一致、重複ID、数量の範囲を確認します。forで各商品を調べ、認証されたDatasetに属し、売上日と同じ年月の販売中商品であることも確認します。検証済みの行をlistにまとめ、不正ならreturnで400の応答を返して保存前に終了します。

    ここで学べる基礎
    Python：if / for / 関数 / list / return
    Web：validation / 400
    Database：Datasetでの絞り込み

  4. DBへ保存する

    商品と日付の組み合わせで数量を追加・更新し、まとめて確定します。

    処理と基礎を読む

    DailySales Modelのテーブルを使い、商品ID・日付・数量をdictにまとめます。本番用のPostgreSQLと通常pytestのSQLiteでは、on_conflict_do_update()で同じ商品・日付があれば数量を更新します。db.session.execute()で全行を保存し、1回のdb.session.commit()でtransactionを確定します。DB例外ならrollback()で取り消し、500を返します。

    ここで学べる基礎
    Python：dict / try / except
    Database：Model / SQLAlchemy / db.session / transaction / commit / rollback

    {{ source_links(['app.py', 'models.py']) }}

  5. 保存結果からDashboardへ進む

    入力画面の成功表示を確認し、「お店の健康診断書（売上分析・ランキング）を見る」リンクを開きます。

    処理と基礎を読む

    保存後はreturn render_template(..., success=True, ...)で入力画面のHTMLを返します。この処理ではリダイレクトはしません。returnで関数が終わるため、後ろにあるGET用の処理には進みません。利用者がリンクを開くと、ブラウザが新たにGET /dashboardを送り、別の関数dashboard()が動きます。

    ここで学べる基礎
    Python：return / 関数の終了
    Frontend：Jinjaの条件分岐 / HTML link
    Web：response / 次のGET

  6. Dashboardで表示する

    保存済みの数量を集計し、ランキングとグラフに表示します。

    処理と基礎を読む

    _get_sales_from_db()がProductとDailySalesをjoinし、Datasetと表示期間で絞ります。数量の合計はDBのdb.func.sum()が担当し、Pythonが結果をdictにしてsorted()で数量順に並べ、グラフ用のlistも作ります。Flaskがdashboard.htmlへ渡し、JinjaがランキングのHTMLを、JavaScriptとChart.jsがグラフを表示します。

    新しい売上サマリーでは本日・週別・月別・年別を切り替え、GET /api/sales-period-summaryで選択期間の売上金額・前期間比・販売個数ランキング・推移を取得します。今週など進行中の期間では経過日数をそろえて比較します。さらに、店舗所在地を設定した管理者が明示操作した場合に限り、過去の天気データを気象提供元から取得して日付ごとにDBへ保存します。GET /api/weather-historyでは保存済みの記録だけを表示し、Guestは天気の取得・保存を実行できません。天気と売上に相関が見えても原因を断定せず、店主の経営判断の材料として扱います。既存の詳細分析は全年度・全月で始まり、期間の「更新」ではJavaScriptのfetch()がGET /api/dashboard-dataを送り、Flaskのjsonify()で返されたJSONから画面を更新します。「本日の売上」は日本時間の今日を別に集計します。

    ここで学べる基礎
    Database：join / query / 集計
    Python：dict / list / sorted()
    Frontend：Jinja / JavaScript / fetch
    Web：HTML response / JSON

    {{ source_links(['templates/dashboard.html']) }}

PythonとWebアプリの接続

for・if・関数はPythonの基礎。request.formはFlask、queryはSQLAlchemy、fetchはJavaScriptです。Pythonから順に、入力を受ける → DBへ保存する → 画面へ返す、という境界を辿りましょう。

if / for
商品登録で、不正な値なら拒否し、複数行を順に検証・更新します。条件分岐と繰り返しです。
関数 / 引数 / return
売上分析の_get_sales_from_db(current_dataset, target_year, target_month)は、対象領域と期間を引数で受け取り、集計結果を返します。
list / dict
売上入力は検証済みの行をlistにまとめます。売上分析は商品名と数量のdictから、グラフ用のlistを作ります。
try / except
売上入力の日付変換の失敗やDB保存の例外を扱い、エラー応答やrollbackへ進みます。
class / import
models.pyのProduct(db.Model)などがデータ構造を表すclassです。app.pyはfrom models import Productなどで別ファイルの定義を使います。
GET / POST
GETは画面や集計の取得、POSTは入力送信や操作に使用。AI取得も利用回数を消費するためPOSTです。Session復元時のGuest活動日時更新など、GETに伴う共通処理もあります。
request / response
request.argsはURLの条件、request.formはフォーム、request.get_json()はJSONを読む入口。応答にはHTML、JSON、リダイレクトやエラーのHTTP状態コードがあります。
JSON / GitとDB
商品カタログのAdmin追加分はJSONと静的画像をGitHubのPRで管理し、merge・Deploy後にテンプレートへ反映します。月次ProductとそのDailySalesはPostgreSQLに保存します。Admin専用POSTではrequest.formで商品情報、request.filesで任意画像を受け、認証・認可・検証の後にGitHub APIへ申請します。
Sessionは2つを区別
Flaskのsessionは認証状態を引き継ぐための仕組み。SQLAlchemyのdb.sessionはDB読み書きの作業単位です。Flaskの標準Session Cookieは署名で改ざんを検知しますが、暗号化された秘密の保管庫ではありません。
CRUD
Create（作成）・Read（読み取り）・Update（更新）・Delete（削除）。店舗メモで一通り確認できます。商品は履歴を残す販売終了、メモはゴミ箱と完全削除を分けています。
transaction / rollback
関連する変更をひとまとまりで確定・取消する仕組み。売上入力では複数行を保存してからcommitし、DB例外ならrollbackします。
validation
入力を保存前に検証すること。商品登録の名前・価格やタスクのID検証が例です。HTMLの入力制限に加え、サーバーでも確認します。
template / Jinja
Pythonが渡したデータをHTMLへ埋め込みます。input.htmlでは商品の繰り返し表示や成功表示に使い、通常の文字列はHTMLエスケープされます。
JavaScript event
タスクのaddEventListener()がclick・pointer・touchなどを受けて、画面の変更やサーバーへの送信につなげます。
pytest fixture
conftest.pyのflask_app、authenticated_client、csrf_tokenが、テスト用DB・認証済みclient・CSRF tokenの準備を共通化します。

6. テストは何を壊さないためにある？

成功画面だけでなく、「拒否されたときにDBが変わっていないか」「他の利用者のデータが混ざっていないか」まで確認します。

  • 入力の境界・不正値 — 商品名・価格・販売数量・メモ本文・タスクタイトルなどの許容範囲を確認します。
  • 認証・権限・CSRF — 未ログインの業務操作、偽装した認証、tokenなしのPOSTを拒否し、公開ページは読めることを確認します。
  • Dataset分離 — 管理者、Guest A、Guest Bの表示・更新・集計・AI入力が混ざらないことを確認します。
  • transaction / rollback — 保存失敗で商品・売上・店舗ツールの変更が一部だけ残らないことを確認します。
  • 日付と期間 — 日本時間の今日、月・年の切替、DashboardのHTMLとAPIの期間一致、スケジュールの日付境界を確認します。
  • CRUD・履歴・並び順 — 販売終了後の売上履歴、メモのゴミ箱と復元、タスクの保存順と一括操作を確認します。
  • 繰り返し・並行処理 — 完了状態の再送、同じ商品・日付の売上更新などを確認。PostgreSQL用にはGuest上限や保存の実並行テストがあります。すべてのUI連打や競合を網羅するという意味ではありません。
  • 表示の安全性 — 入力文字のエスケープ、URL処理、セキュリティヘッダー、共通navigationを確認します。
  • DB構造の変更 — migrationのupgrade / downgrade、既存データの保全、DB制約を確認します。

Q2. GETとPOSTをどう使い分けている？

答えを見る

Q3. db.session.commit()は何を確定する？

答えを見る

db.session.commit()は、そのtransactionのDB変更を確定します。add()は保存対象の追加、売上入力で使うexecute()はSQLの実行ですが、それだけでは確定しません。全行を処理してcommitが成功すると変更が確定し、DB例外時はrollbackで取り消します。

Q4. return redirect(...)の後、同じ関数の後ろは動く？

答えを見る

後ろの通常の処理には進みません。returnは関数を終了し、redirect()の応答を返します。ブラウザが移動先へ送るGETは別のリクエストです。売上入力はredirectではなく、成功表示付きのrender_template()をreturnします。いずれも、同じ関数の後ろに続けて進む処理ではありません。

Q5. SQLAlchemyのModelは何のためにある？

答えを見る

Modelは、DBのテーブル・列・関連・制約をPythonのclassで表すためのものです。たとえばDailySales.product_idでProductに売上が結び付き、商品IDと日付の一意制約で重複行を防ぎます。Modelはデータの構造であり、入力値の検証やDatasetの認可も別途必要です。

Q6. JinjaとJavaScriptの主な役割はどう違う？

答えを見る

Jinjaはサーバーで、Pythonから渡された商品や集計をHTMLに埋め込みます。JavaScriptはブラウザで、クリックへの反応やJSON取得後の表示変更を行います。Dashboardは最初のランキングをJinjaで表示し、期間更新はJavaScriptのfetchで取得した値から表示し直します。

Q7. pytestでrollback後のDBまで確認するのはなぜ？

答えを見る

エラー応答が返っても、一部の行だけ保存されている可能性があるからです。複数行の保存途中でDB障害を起こし、rollback後の件数・値が変更前と同じか確認します。これで「失敗時に半端な保存を残さない」というtransactionの保証を検証できます。

Q8. 認証のSessionとdb.sessionは同じもの？

答えを見る

役割が違います。FlaskのSessionはFlask-Loginとともに、リクエストをまたいで認証状態を引き継ぎます。db.sessionはSQLAlchemyがDBの読み書きとtransactionを管理する仕組みです。認証状態だけで商品を選ぶのではなく、認証された利用者のDatasetにqueryを限定します。
