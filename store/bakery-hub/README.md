## ホームカードと当日・週間予報（v3.1 Phase 2B）

現在・次の予定、今日のスケジュール、Adminの出勤予定、BakeryNewsはカードの空白部分からも一覧へ進めます。既存の予定詳細・新規登録・スタッフ登録・記事リンクは個別の行き先を優先します。CSSで既存の主リンクをカード全体へ広げており、リンクの入れ子やJavaScriptによる二重遷移はありません。本日の売上を維持し、「次の作業へ」は商品一覧・販売・店舗メモの48px以上のボタン型リンクにしています。販売先は既存の公開切替条件に従います。キーボードでは各リンクをTabで選んでEnterで移動できます。

「今日の天気」カードは地域・区分・アイコンと、提供された場合は今日の日内最大降水確率を示します。カード全体から専用の `/weather` へ進み、当日の予想気温・降水確率・対象時間帯、当日を含む最大7日間、出典、予報対象時刻と取得時刻（JST）を確認できます。スマホでは日別の縦一覧、広い画面では自動折返しのグリッドです。取得できない数値は「未提供」と表示します。

| 提供元 | 気温・天気 | 降水確率 | 条件 |
|---|---|---|---|
| MET Norway Locationforecast compact | 同じレスポンスの時刻別気温をJST日付で集計。全24時間が揃わない日は「取得分最高／最低・時間帯限定」。揃った日も時刻別予想値の最大・最小。アイコンは正午に最も近い提供時刻の予報で、代表時刻を併記 | 日本向けglobal compactでは未提供。降水量から代用しない | 提供期間から最大7日。先の日は6時間間隔などのため全日の極値を保証しない |

実装は `current_weather.py`（既存取得とキャッシュ）、`home_forecast.py`（日別の検証・集計）、`static/home_weather.js`（表示用書式）、`static/store_home.js`（ホーム表示）、`static/weather_detail.js`（専用ページ表示）です。合成データのpytest／Nodeテストと、390px・タブレット横向き・1280pxのChromium E2Eで確認します。実機での今回のカード操作・予報表示は別途確認が必要です。

## 商品・写真・レシピのCSVバックアップ

独立CLI `data_vault.py` は、Adminの商品名・単価・分類・販売状態・表示順・写真、レシピ・材料・商品との対応だけをローカルへ保存し、スキーマ準備済みの空Admin Datasetへ復元します。管理画面やDocker起動処理には組み込みません。既定はdry-runで、書込には復元先Datasetの明示確認が必要です。内部IDを対応づけ直し、途中失敗は全体rollback、保存後はDBから読み戻して照合します。

保存形式はUTF-8の4 CSV・写真・件数とSHA-256を持つManifestです。写真は再圧縮せず、CSVの日本語・改行・引用符を保持し、数式対策用のアポストロフィを読込時に取り除きます。商品写真はWebPの元内容を復元し、レシピのstatic画像には復元先の同じ承認素材が必要です。

**実売上・会計・返金・価格変更監査履歴・日次売上・個人情報・認証・未同期会計は対象外です。DB全量バックアップの代わりにはなりません。** 無料DBの期限前に承認した作業窓で最終保存し、以後の更新と別途の本番移行を区別します。Private GitHubへの自動push・DB切替は行いません。実データの書き出し・アップロードは別途承認が必要です。

[保存・dry-run・復元の手順と制限](docs/data-vault-guide.md)／[Private保管庫の初期構成（架空データのみ）](docs/data-vault-template/README.md)。Phase 7の正式レジ公開判定はNO-GOを維持します。

`seed_demo.py` は旧商品・旧売上で投入要否を判断します。通常のDocker起動からは外し、復元済みDBでは実行しません。明示的な保守操作は [Web起動とDB保守の分離](docs/startup-maintenance.md) を参照してください。

## ホーム画面から起動するPWA（2026-10-19）

PWA（Progressive Web App）は、Webアプリを端末のホーム画面などへ追加して、アプリのように起動する利用方法です。Bakery Hub全体を一つのアプリとして扱い、スマホ・タブレットでURLの入力やタブの選択を減らします。ホーム、売上分析、商品・仕込み・スタッフ・予定・発注・メモ・タスク、レジは、既存の画面と認証をそのまま使用します。同じリポジトリにある他アプリは変更しません。

**正式レジの本番切替は引き続きNO-GO。PWAのインストールは、全機能のオフライン化・正式レジの有効化・自動ログインを意味しません。** 本番へ反映する操作は別途の承認が必要です。PWAの実機確認はユーザー報告で異常なしです。端末別の詳細条件は未記録で、今回の端末別レジUIとiOSは実機未検証です。

### Androidで追加・起動する

1. AndroidのChromeで、HTTPSのBakery Hubを開きます。アプリ内ブラウザやシークレットモードを避け、通常のChromeを使います。
2. Chromeの「⋮」メニューから「アプリをインストール」または「ホーム画面に追加」を選び、表示名が **Bakery Hub**、麦のアイコンになっていることを確認して追加します。文言や追加方法はOS・Chromeの版により異なります。自動のインストール案内は保証しません。
3. ホーム画面のBakery Hubアイコンを押します。既存の `/home` から起動し、未ログイン・セッション期限切れの場合は従来の `/login` へ進みます。既存のAdminログイン・Guestデモを選択してください。インストール自体は認証や権限を付与しません。
4. 通常のURLバー・タブを省く `standalone` 表示を確認します。Androidのシステムバーやアプリ切り替えはOS側の動作を維持します。画面の縦横を固定しません。通常のChromeタブからの利用も引き続き可能です。

インストール項目が見つからない場合はHTTPS・通常モード・Chromeの版・管理端末の制限を確認します。インストール済みの場合は同じアイコンを使用してください。ブラウザによっては通常のショートカットになるため、実機でアイコン起動後の表示を確認する必要があります。

iPhone / iPadではSafariの共有メニューから「ホーム画面に追加」を選びます。「Webアプリとして開く」が表示される場合はオンにして追加します。これは[Appleの案内](https://support.apple.com/ja-jp/guide/iphone/iphea86e5236/ios)に基づく手順で、Bakery Hubの実iOSでの起動・セッション共有・レジ保存は未検証です。Cookieや保存領域の共有、表示方法はOS・ブラウザにより異なります。

### オンライン利用・レジ用Service Worker・更新

**今回アプリ全体用のService Workerは登録しません。** [Chromeチームのインストール要件](https://web.dev/articles/install-criteria)と[メニューからのインストールに関する説明](https://developer.chrome.com/blog/update-install-criteria)を確認し、Manifest方式を選びました。Service Workerは通信を扱う仕組み、Manifestはインストール後のアプリ名・起動・表示を伝える設定で、役割が異なります。インストールを目的に認証画面や売上APIをキャッシュするWorkerを足しません。

- 既存Workerの登録URLは `/register/offline-sw.js`、scopeは `/register/`。登録は従来のAdmin端末準備操作時だけで、機能フラグと端末許可の条件を維持します。新しい登録との範囲重複・優先関係は生じません。
- `register_offline_sw.js` の版・キャッシュ対象・更新方法は変更しません。Cache Storageは情報を含まない専用シェル、許可されたレジ資産などの保存先です。認証済みプレビューHTML・Cookie・売上API・認証APIを追加保存しません。IndexedDBは暗号化済み準備情報・下書き・未同期会計を保持する別の保存先で、初期化・削除しません。
- ホーム・通常の業務画面はオンラインで使います。準備済みレジの専用URLからの通信断復帰、PIN、期限付き端末許可、会計の端末保存・再同期は従来どおりです。オフラインでアプリアイコンを押してホームからレジへ進めることは保証しません。端末準備していないレジもオフライン化されません。
- 通常画面はオンラインで再読み込み・開き直すとサーバーの最新版を取得します。Manifest・アイコンの反映時期はブラウザ・OSによります。アイコン名や絵柄が即時更新される保証はありません。通常画面の更新のために再インストールする必要はありません。
- レジ用Workerの更新待ちは従来の案内に従い、会計を端末保存して未同期記録を確認し、全レジタブ・ウィンドウを閉じて開き直してから再準備します。`skipWaiting`による強制更新・自動リロードは追加しません。既存端末のキャッシュ済みシェルには、既存の再準備まで新しいPWAメタ情報がない場合がありますが、未同期会計は保持します。
- 更新・トラブル対応のためにサイトデータ、IndexedDB、Cache Storageを削除しないでください。アンインストールやブラウザの保存領域整理も未同期データへ影響し得るため、未同期会計を残したまま行わないでください。PWAはネイティブアプリではなく、ブラウザ側の保存容量・削除ポリシーに従います。

アイコン原稿の再出力は、開発用のCairoSVGで各サイズのPNGを生成できます（本番依存は追加しません）。例：`cairosvg static/pwa/icon-source.svg -o static/pwa/icon-192.png --output-width 192 --output-height 192`。他の3サイズも表の寸法へ出力し、絵柄・不透明背景・maskable安全領域を確認します。

## 商品管理統合・端末別レジ表示（2026-10-19更新）

正式レジの本番切替は引き続き **NO-GO**。この変更は作業ブランチの実装であり、本番DB・Render設定・機能フラグは変更しない。以下を現行仕様とし、後述のPhase別記録に残る「500円上限」「18品必須」「独自商品別枠」「画像アップロードなし」は当時の実装記録として読む。

- Adminの商品管理フラグが有効な環境では、`/products` の「商品一覧」を入口にする。旧 `/register/products` と旧月次登録 `/` のGETは商品一覧へ案内する。旧月次登録は一覧内の履歴用リンク（`/?legacy=1`）から参照可能。Guestの月次登録・日次売上入力は変更しない。フラグ既定OFFの環境は従来画面を維持する。
- 正本は既存の `RegisterProduct`。パンの種類（8種類）と商品分類（定番・季節もの・特別商品）、写真、価格、`is_active`を同じIDで管理する。既存行の分類は推測せず「その他・定番」を初期値とする。必要な商品を店主が分類する。
- 新規登録・編集は同じ写真中心のフォーム。承認済み画像、写真ファイル、スマホ撮影を受け付け、名前・価格・分類とともに確認ダイアログを表示する。写真なしなら文字タイルを維持する。
- 写真は既存 `catalog_repository.validate_image()` で拡張子・MIME・実画像・10MiB上限・画素数・単一フレームを検証し、メタデータを除いて500KiB以下のWebPへ変換。`RegisterProduct.photo_webp` に保存し、Renderの一時ファイルへ置かない。既存承認画像は `image_key` のまま使い、新規写真と同時に二重保持しない。認証済みの所有Datasetだけが写真URLを読める。写真の保存量は商品数に比例するため、DB容量とバックアップ容量も運用時に確認する。
- 終売は `is_active=False`。一覧下部に残し、新規レジのカタログから除く。同じID・写真・分類・価格履歴・仕込み対応・過去売上のまま、価格確認後に再開できる。通常UIに物理削除はない。
- 18商品は初期候補。管理画面やAdminレジのGETでは生成しない。確認付きPOSTだけが不足候補を追加する。既存品の変更や終売解除はしない。内部 `template_key` とGuest開発プレビューの初期化互換性は維持する。18品すべての登録・販売を切替条件としない。
- 新規登録はUUID送信キーと内容digest（写真・分類も含む）で再送を識別する。更新・終売・再開は署名したDataset・商品ID・版番号、Datasetロック、CSRFで保護する。同一更新の直後の再送は許容し、別編集や終売→再開後の古いフォームは409で拒否する。価格変更時だけ `RegisterPriceHistory` に追記する。
- 商品単価は整数 **0〜100,000円**。商品、価格履歴、会計明細、復旧明細、同期時の表示価格照合に同じ上限を適用。数量±50・1会計50商品・会計合計の既存上限は維持する。0円合計会計は保存不可。既存の承認価格資料や実売価は推測で変更しない。

- タブレットの右会計は明細だけがスクロールし、合計・預り・お釣り・完了を常時操作できる。ヘッダー・説明を小さくし、商品見出しの横に前後操作を配置する。表示専用register_layout.jsが実際の要素高と可視画面高を測り、収まるときだけ1画面へ配置する。低い画面・文字拡大・長い警告は通常の縦スクロールへ戻し、操作をoverflowで隠さない。端末準備・保存照会はヘッダーから開くダイアログへ移し、要確認・失敗・同期状態の通知と破棄確認を維持する。
- `register_cash_pad.js`は0〜9・00・C（全消去）・末尾1桁削除を提供する。金額は円単位・桁区切りで表示し、入力欄やソフトキーボードへの操作は不要。キーパッド内ではPCの数字・Backspace・Delete/Cも使える。先頭ゼロを正規化し、整数0〜1,000,000,000円を受け付け、上限超過は元入力を保持して通知する。既存inputイベントを経由して計算・下書きを更新する。会計完了後はリセット、返金では預り操作を隠し、処理中やデモ完了後はキーパッドを無効にする。
- スクロール処理は会計状態に触れない。数量・預り・釣銭・返金を維持する。非保存デモも同じスクロールとキーパッドを使うが、保存用JSを読まない。オフラインシェルはv4の同じ版のキャッシュから表示制御・キーパッドを読み込み、旧キャッシュや未同期キューは削除しない。資産URLにも同じ版番号を付け、旧Workerが更新待ちの場合は準備完了にせず、全レジタブを閉じて再準備するよう案内する。強制activateはしない。
- オフライン準備時は写真をdata URLとして既存の暗号化カタログ内に含める。認証付き写真をService Workerの公開画像キャッシュへ追加しない。元会計の価格・スナップショット・営業日・送信キー・未同期記録をページ操作やマスタ変更で更新しない。既存の署名商品版によるオフライン受入、通常会計の価格差・要確認・再送防止を維持する。オフライン自動受入は既存の1会計50,000円までを維持し、それを超える会計は元記録を残して管理者確認へ回す。
- 旧 `Product`・`DailySales` に自動移行・同名統合・金額更新・削除はしない。旧商品のコピーは明示確認した別IDとして登録し、売上自体はコピーしない。既存の `RegisterPrepLink` と標準品のレシピキーは変えない。

### スキーマとマージ前の停止条件

**Phase 5Cでは**価格履歴、本番用のAdmin認可と機能フラグ、切替日確定処理、根拠を確認する過去日復旧経路、PIN付きオフライン起動用シェル、承認済み翌営業日の自動同期を実装しました。端末保存後は通信復旧を待たず次の会計へ進めます。隔離PostgreSQLとChromiumのブラウザ試験は成功しましたが、実スマホ・タブレット、本番バックアップ・復元、全端末確認は未検証です。本番公開可能とは判定していません。

技術設計は[レジv3.0設計書](docs/v3-register-design.md)、実機・端末・バックアップとPhase 7の切替条件は[正式レジ切替手順書](docs/v3-register-cutover-runbook.md)を参照してください。実際の運用開始は別途確認が必要です。

### 店舗運営ホーム・スケジュール

ログインまたはGuest Demo開始後は、商品登録とは独立した **ホーム** を開きます。今日の予定を時刻順に確認し、開始時刻・終了時刻のある現在の予定と次の予定を見られます。予定は登録・編集・削除でき、日本時間で表示します。ホームを開いたままでも時計と予定を更新します。時刻が来ただけでは予定を完了扱いにしません。

天気は設定地点の**現在のモデル推定または直近の予報**を表示します。過去の天気記録とは別の情報です。GPSは使わず、設定や通信が不足する場合は取得できない理由を表示します。地点には `WEATHER_LATITUDE`・`WEATHER_LONGITUDE` を設定し、`WEATHER_LOCATION_NAME` で表示名を指定できます。広島市中心部の例は GeoNames の[広島市地点](https://www.geonames.org/1862415/hiroshima.html)（北緯34.4、東経132.45）です。店舗に合わせて変更できます。

気象庁の広島県予報を利用する場合は `WEATHER_API_MODE=jma` と `WEATHER_JMA_AREA_CODE=340010`（広島県南部）または `340020`（広島県北部）を、店舗の所在地に合わせて明示します。地域名や緯度経度から区域を推測しません。設定を変更しない限り既存モードが動き、本番環境の設定はこのPRでは変更しません。[気象庁の広島県予報JSON](https://www.jma.go.jp/bosai/forecast/data/forecast/340000.json)をHTTPSで取得し、固定URL・6秒タイムアウト・256KiB上限・発表日時／区域／配列整合性検査を通した上で10分キャッシュします。JSONはWeb向けのため形式変更の可能性があります。失敗時は古い予報へ自動的に切り替えず取得不可とします。短期の天気・6時間帯別確率は指定した南部／北部の値、週間の3日目以降は広島県全域の天気・当日確率で、一覧にその区域を表示します。短期の翌日も指定区域の最初の6時間帯を表示し、期間全体の確率には換算しません。気温は別地点の値を区域全体の気温として扱わず、気象庁モードでは表示しません。出典：[気象庁ホームページ](https://www.jma.go.jp/jma/kishou/info/coment.html)（予報を表示用に加工）。気象庁の公開JSONは予告なく変更され得るため、切替時には実際の店舗区域、取得と画面表示を確認してください。

本番で無料の予報を取得する場合は `WEATHER_API_MODE=met_norway` を指定し、`WEATHER_API_KEY` は空欄にします。MET NorwayのLocationforecastは観測記録ではなく予報です。運用時には[利用条件](https://api.met.no/doc/TermsOfService)を守り、画面上で出典と[CC BY 4.0](https://creativecommons.org/licenses/by/4.0/)を示します。識別可能なUser-Agentを付け、地点を小数4桁へ丸め、レスポンスのExpiresまでキャッシュし、再取得時はLast-Modifiedがあれば条件付きリクエストを送ります。直近の予報がない場合や古い場合は天気を表示しません。無料APIの可用性保証はありません。このモードは過去天気の取り込みには対応しません。

MET Norwayの正常な予報をホームで取得したときは、認証・CSRF保護された保存リクエストで、現在のDatasetに日本時間の**その日最初の予報**を1件だけ記録します。予報コード、対象時刻、取得時刻、地点、出典を`daily_forecasts`へ保存します。売上ダッシュボードでは日付単位の売上推移に保存済み天気のアイコンを表示し、選択して詳細を確認します。過去の気象データと予報が同日にある場合、アイコンには過去の気象データを優先し、詳細には両方を表示します。履歴閲覧では気象APIへ通信しません。従来の`daily_weather`（過去の観測・再解析データ）とは別に保存し、双方を上書きしません。**保存値は取得当時の予報であり、実際の観測結果ではありません。** ホームを開かなかった日や取得に失敗した日は記録されません。Guestの記録はDataset期限切れ時に削除されます。

本番では新しいmigrationをデプロイ前に適用する必要があります。既存の`daily_weather`と売上データは変更しません。Render無料PostgreSQLを新しいDBへ切り替える場合、保存済みの予報や既存データは自動移行されず、別途バックアップ・復元が必要です。

Open-Meteoを使う場合は、商用の契約済みAPIキーで `WEATHER_API_MODE=commercial` と `WEATHER_API_KEY` を設定します。Open-Meteoの無料APIは、既存どおりローカルの非商用開発に限る `WEATHER_API_MODE=noncommercial` と `LOCAL_DEVELOPMENT=true` の組み合わせだけで利用できます。公開ポートフォリオの非商用該当性が不明な状態で、本番へ `LOCAL_DEVELOPMENT=true` を設定しないでください。

### スタッフ・シフト管理（Admin専用）

サイドメニューの「スタッフ・シフト管理」から、表示名・担当（製造／販売／兼任／その他）・任意の入社日を登録できます。一覧は名前・担当・在籍状態をコンパクトに示し、行を開いた詳細画面で入社日と編集・退職・復職操作を確認します。退職時は在籍状態を変更し、過去の勤務予定は残します。同姓同名でもIDで区別します。Guest Demoにはメニューを表示せず、URLを直接開いてもスタッフ情報を取得できません。

日別には1人・1業務日につき「出勤予定」「終日（時刻未指定）」「休み」のいずれかを1件登録します。終日は24時間勤務ではなく、開始・終了時刻のない予定です。休み・未登録とも区別します。新規の時刻付き予定は日本時間の同一日内で、開始から終了まで最大12時間（モデル店舗の運用ルール）。時間帯の重複を拒否します。以前登録された翌日終了・12時間超の予定は自動変更せず、詳細表示と備考のみの編集では元のUTC日時を維持します。時刻を変更する場合は新ルールを適用します。PCは月間カレンダー、スマホは横スクロールの日付選択とコンパクトな日別一覧を使い、行を開くと備考・編集・取り消しの詳細画面へ進みます。これは**予定の管理**であり、勤怠打刻や勤務実績ではありません。

Adminホームの「今日の出勤予定」は、既存の `planned_work_for_day()` を使って、認可済みAdmin Datasetと `business_today()` のJST業務日に登録された出勤・終日予定を読みます。休みは人数に含めず、終日は「終日（時刻未指定）」、既存の翌日終了はその旨を表示します。4人までをコンパクトに並べ、残り人数とシフト表へのリンクを示します。スタッフ未登録と本日の予定なし、DB取得失敗は別の文言です。Guestはスタッフの検索も表示も行いません。表示は予定であり、実際の出勤や勤務中を意味しません。ホームのGETはスタッフ・シフト情報を書き換えません。

保存先は`shop_staff`・`shop_shifts`テーブルで、`ShopSchedule`とは独立しています。新revision `d5a9f1b7c204` は `c8e6a1b9d4f2` の後に適用し、`shop_shifts` のCHECK制約だけを拡張します。既存行の時刻と状態は維持します。本番反映前にバックアップと現在のAlembic revisionを確認し、先にmigrationを適用してから新コードを起動してください。通常のDocker起動ではmigrationを実行しません。適用は独立した保守操作とします。このPRでは本番DBへ適用しません。終日予定が残る間のdowngradeはデータ損失を避けるため拒否されます。さらに以前のrevisionへのdowngradeはスタッフ・シフト表自体を削除するため実行しないでください。

### 仕込み管理（Admin専用）

仕込み画面の「レシピを登録・編集する」から、標準18品・承認済みAdminテンプレート、または登録済みのオリジナル月次商品を選び、基準個数、材料名・使用量・単位（g / ml / 個）、仕込みメモを登録します。配合の自動生成はしません。テンプレートは安定したキー（`template:<key>`）、自由入力の商品は選択した月次ProductのID（`product:<id>`）を識別子に使います。商品名が同じというだけで統合せず、レシピは月次Productから独立しているため翌月以降も使えます。別月に同名の自由入力商品を登録した場合は、既存レシピを仕込み画面から使い、商品名による自動関連付けはしません。

サイドメニューの「仕込み管理」（`/prep`）ではJSTの今日を開き、①パンを選ぶ → ②製造個数を決める → ③必要材料を見る、の順に操作します。保存済み予定は日付ごとに復元し、複数商品を**まとめて保存**できます。選択を外すだけでは保存済み予定を削除せず、0個も予定として保存できます。削除は折りたたみ内の明示的な操作です。レシピの登録・編集は別の「レシピ管理」（`/prep/recipes`）で行い、従来の `/prep/plans` と単品保存URLも利用できます。

個数は±ボタンで現在値から10個ずつ調整でき、数字欄をタップすれば1個単位の任意の整数（0～1000個）を直接入力できます。端数を10の倍数に丸めず、範囲の端では0または1000で止まります。JavaScriptがその場で材料を試算し、未保存の変更を示します。サーバーは選択したレシピIDと個数を全件検証し、一度のtransactionで更新またはrollbackします。Pythonでは `Decimal` で `使用量 × 予定数 ÷ 基準個数` を計算し、材料名の前後空白を除いた同名・同一単位だけ合算します。小数第6位まで不足しない方向へ表示し、別単位の換算はしません。過去の日付の表示も**最新レシピによる再試算**であり、当時の実績や製造完了記録ではありません。

商品別の内訳と「在庫と比較する」は任意で開けます。現在量は画面内だけの入力で、未入力は「未確認」です。数量変更や開閉の際も入力済みの値を維持し、DB保存や自動減算はしません。既存の材料発注リストへ移動できますが、自動発注は行いません。発注メモに `電話：082-123-4567` のように独立した行を書くと、妥当な国内電話番号のみ `tel:` リンクを表示します。リンクを押すまで発信しません。Guestには仕込みメニューもデータも公開しません。

新revision `e2a7c4d9b105` は `d5a9f1b7c204` の次です。`prep_recipes`・`prep_ingredients`・`prep_plans` を追加し、Datasetとレシピの複合外部キー、一意制約、数量制約で不正な関連付けや二重保存を防ぎます。既存のProduct・DailySales・材料発注・スタッフのテーブルや行は変更しません。本番反映時はバックアップとrevisionを確認し、新コードを起動する前にmigrationを**一度だけ明示的に**適用してください。通常のDocker起動ではmigrationを実行せず、revision不一致なら起動を拒否します。downgradeは仕込みの新規テーブルと保存済みのレシピ・予定を削除するため、本番で安易に実行しないでください。

### 製造実績・廃棄ロス（Admin専用）

仕込み管理の「製造実績・廃棄ロスを記録する」から `/prep/waste` へ移動します。日本時間の営業日と商品を選び、実際に完成した個数、実際に廃棄した個数、任意のメモを保存します。片方の個数だけでも記録でき、空欄は未入力、`0` は確認済みの0個です。日別一覧で保存値を確認・修正できます。商品名は保存時の表示名を保持し、改名・終売後も履歴を識別できます。継続商品（RegisterProduct）と旧月次商品（Product）は別IDで扱い、同名でも月が違えば統合しません。レシピ未登録の商品も選択できます。

新テーブル `waste_records` はDataset・営業日・商品を一意に結び、商品へのDataset付き外部キー、数量CHECKと一意制約で越境・負数・重複を防ぎます。予定（PrepPlan）と販売数、商品マスタは変更せず、予定数や販売数から廃棄を推定しません。廃棄が当日の実製造数を超えても前日持ち越しを考慮して拒否せず、画面で再確認を促します。今回のAlembic revisionは `c8d3e7f1a204`（親 `b6d2e9f4a107`）です。既存のproductsにDataset複合参照用UNIQUE制約を追加しますが、商品と売上の行は変更しません。**Draft PRのまま本番DBには適用しません。** 本番反映では先にrevision・バックアップ・停止時間を確認し、明示的なmigrationを適用してからコードを起動する必要があります。通常起動のstartup_guardはrevision不一致を拒否します。downgradeは保存した実績を失うため、本番で実行しないでください。

店舗レイアウトは **準備中** です。架空のスタッフやレシピを登録・表示しません。Taskは既存の店舗メモツールが管理し、スケジュールの予定とは別です.

> Renderの無料インスタンスを使用しているため、しばらくアクセスがない場合はスリープ状態になります。  
> 最初のアクセス時のみ、起動に時間がかかる場合があります。

## 📖 プロジェクト概要

ベーカリー店舗の日々の商品管理・売上入力・分析と、店舗内の小さな業務を一つにまとめるWebアプリケーションです。

現在の通常画面と、実装済みだが明示的な設定が必要な試験機能を区別しています。下記は通常の業務フローです。

```text
売上管理
├── 商品一覧（共通商品管理、または旧月次登録 / 過去履歴への入口）
├── 日次売上入力
├── 売上分析Dashboard
└── Geminiによる経営アドバイス

店舗運営
├── スタッフ・シフト管理（Admin専用）
├── ホーム（今日の予定・次の予定・設定地点の現在の天気）
├── スケジュール（予定の登録・一覧・詳細・編集・削除）
├── 仕込み管理（Admin専用・レシピ・製造予定・材料集計・在庫比較）
└── レジv3.0（試験機能・正式本番レジは未公開）

店舗メモツール
├── 材料発注リスト
├── 店舗メモ
└── タスク
```

利用者は、次の2種類を明確に分けています。

```text
/login
  │
  ├── Admin
  │     └── 管理者専用Dataset
  │
  └── Guest Demo
        └── Guestごとの一時Dataset
```

AdminとGuestは同じ業務画面を利用できますが、  
参照・更新するデータは認証されたidentityからサーバー側で決定します。

利用者が外部から任意の`dataset_id`を指定して、別Datasetへ切り替える設計にはしていません。

## 📊 現在の通常運用：日次売上管理の3ステップ

### 1. 商品メニューと価格を登録する

Guestと旧入力用の月次登録では、対象月の商品名と価格を登録します。標準18種から選ぶと商品名・代表画像・初期価格が設定され、自由入力での商品追加も可能です。

登録済み商品の更新は商品IDを基準に行います。テンプレート商品は商品名を固定表示し、実際の売価は初期価格と分けて管理します。

販売終了商品は物理削除せず、

```text
is_active = False
```

とする論理削除方式です。

これにより、販売終了後も過去の売上履歴を維持できます。

Guest Demoでは、1 Datasetにつき最大30商品まで登録できます。商品名は1〜100文字、売価は0〜9,990円の10円単位です。日次売上の販売数量は0〜1,000個を扱います。

---

### 2. 本日の販売個数を入力・更新する

日次売上入力画面では、商品ごとに現在保存されている数量を表示します。

```text
高級食パン
🟢 本日の登録済み：14個
```

入力欄にも現在値を表示します。

14個登録済みの商品へ17個を入力した場合、

```text
14 + 17 = 31
```

ではなく、

```text
14 → 17
```

と更新します。

そこで画面上でも、

```text
💾 本日の売上個数を更新する
```

と表現しています。

また、入力欄へフォーカスした際には現在値を選択状態にし、

```text
30
↓
35を入力
↓
35
```

となるよう、既存値を削除する手間を減らしています。

---

### 3. 売上分析・ランキングを見る

ダッシュボードでは、

- 商品別売上ランキング
- 本日の売上金額（日本時間）
- 売上数量グラフ
- 年月別集計
- 販売終了商品の過去売上
- Gemini APIによる経営改善提案

などを確認できます。

PR #49では、棒グラフ周辺のUIとPC / スマートフォンのレイアウトを見直し、グラフを読み取りやすく操作しやすい構成へ調整しました。

PR #58では、表示中の年月にかかわらず、認証済みDatasetの当日売上を「登録単価 × 販売数量」で集計するKPIを追加しました。該当する売上がなければ0円を表示します。
売上推移とランキングは独立したカードです。スマホではランキングの最初の約3.5件を表示し、カード内をスクロールすると全順位を確認できます。端ではページのスクロールへ自然に引き継がれます。PCではランキングを全件表示します。商品ごとの売上横棒グラフと年月指定分析は引き続き利用できます。

月の選択欄では、売上データ（`DailySales`）が存在する月に「登録済み」と表示します。

```text
10月（登録済み）
```

商品登録画面でも商品を登録した月に「登録済み」と表示しますが、判定条件は異なります。**商品登録画面はProductの登録状況、DashboardはDailySalesの存在**を示しています。

表示年月を変更した場合は、

```text
🔍 データを抽出
```

を押してDashboardを更新します。

<details>
<summary><strong>🛒 材料発注リストを見る</strong></summary>

<br>

材料発注は、売上用のProductとは独立した`MaterialOrderItem`として管理します。

主な項目は、

```text
name           最大100文字
quantity_text  最大30文字
memo           最大300文字
is_completed
created_at
completed_at
```

です。

1 Datasetにつき最大100件とし、新規作成時はDataset rowをlockしてから件数を再確認します。  
これにより、PostgreSQL上で同時requestが発生した場合でも上限超過を防ぎます。

完了状態の変更と削除も、現在のDatasetに所属するitemだけを取得し、row lockを行ってから更新します。

`is_completed = true` のときだけ `completed_at` を持つようDB CHECK制約でも整合性を確認しています。

DB例外時はrollbackし、別Datasetのitem IDを送られても更新対象にしません。

</details>

<details>
<summary><strong>🗂 DatasetによるAdmin / Guest分離を見る</strong></summary>

<br>

Guest Demo公開にあたり、`Dataset`をデータ境界として導入しました。

```text
Dataset
├── Admin Dataset
├── Guest Dataset A
├── Guest Dataset B
└── Guest Dataset C
```

Product・MaterialOrderItem・ShopMemo・ShopTaskは、それぞれ所属する`dataset_id`を持ちます。

商品・日次売上・Dashboard・AI分析・材料発注・店舗メモ・タスクなどの処理では、  
現在認証されている利用者が利用できるDatasetだけを対象にします。

```text
Guest A
↓
Guest Bの商品・売上を参照しない

Guest
↓
Adminの商品・売上を参照しない
```

Guest AからGuest Bの商品IDを送信した場合でも、  
現在のDatasetに所属する商品として解決できなければ更新処理へ進みません。

Dashboardについても、

```text
HTML表示
API集計
売上存在月
ランキング
AI prompt
```

までDataset単位で絞り込みます。

外部から`dataset_id`を送信して対象Datasetを切り替える方式ではなく、  
認証済みidentityからサーバー側でDatasetを決定します。

既存のAdminデータについては、Alembic migrationを利用して、

```text
Datasetテーブル追加
↓
Admin Dataset作成
↓
既存ProductをAdmin Datasetへbackfill
↓
Product.dataset_idをNOT NULL化
```

という段階的な移行を行いました。

> [**補足**]
> 一般的な複数ユーザー・複数店舗向けtenant機能を完成させたという意味ではありません。  
> 現在は単一Adminと一時Guest Datasetを分離する構成です。

<details>
<summary><strong>⏱ Guest Datasetの期限・cleanupを見る</strong></summary>

<br>

Guest Datasetでは主に、

```text
created_at
last_activity_at
absolute_expires_at
```

を管理します。

現在の期限は、

```text
無操作期限
30分

絶対期限
2時間
```

です。

無操作期限は利用中の活動によって更新されますが、  
絶対期限は延長しません。

Guest Datasetの利用時には期限を確認し、期限切れの場合は業務処理へ進ませません。

さらに新しいGuest Session作成時には、期限切れGuest Datasetをcleanupします。

削除順序は、

```text
MaterialOrderItem / ShopMemo / ShopTask
            ↓
        DailySales
            ↓
          Product
            ↓
          Dataset
```

です。

Admin Datasetや有効Guest Datasetはcleanup対象へ含めません。

### cleanup競合対策

最初の期限判定時には期限切れだったGuestでも、  
削除直前までに利用者が操作して`last_activity_at`が更新される可能性があります。

そこで削除候補をそのまま信用せず、

```text
期限切れ候補を取得
↓
削除直前に最新rowを再取得
↓
row lock
↓
期限を再判定
↓
まだ期限切れなら削除
```

という流れにしています。

これにより、

```text
最初は無操作30分超過
↓
利用者が操作して活動時刻更新
↓
古い判定だけを使って削除
```

という事故を防ぎます。

次のようなケースもテストしています。

- 絶対期限切れ
- 無操作期限切れ
- 境界時刻
- 有効Guest保持
- Admin保持
- cleanup冪等性
- cleanup途中のDBエラーとrollback
- 同時cleanup
- cleanupとGuest活動の競合

</details>

<details>
<summary><strong>🤖 Gemini API・Guest AI利用制限を見る</strong></summary>

<br>

Gemini APIはページ表示だけでは実行しません。

```text
日次売上入力
└── 今日のひとことを聞く

Dashboard
└── 詳しいアドバイスを聞く
```

利用者が明示的に操作したときだけAPIを呼び出します。

Guest Demoでは、

```text
/api/greeting
+
/api/ai-advice
=
合計3回
```

まで利用できます。

1 Guest Datasetごとに独立した回数を管理します。

```text
Guest A
3回

Guest B
3回
```

のように、別Guestの利用回数は混ざりません。

4回目以降はHTTP 429を返し、Gemini APIへ進みません。

### atomicな利用権確保

単純な、

```text
SELECT
↓
Pythonで回数確認
↓
+1
```

では、同時request時に上限を超える可能性があります。

そこでDB側で条件付きUPDATEを行い、

```text
guest_ai_usage_count < 3
期限内
現在のGuest Dataset
```

を満たした場合だけ1回分の利用権を確保します。

commit後にGemini APIを呼び出すため、  
Geminiの応答待ち中にDB transactionを保持し続けない構成です。

Gemini API側で、

```text
429
503
timeout
その他のAPIエラー
```

が発生した場合でも、すでに確保した利用回数は戻しません。

一方、

```text
API Keyがない
対象売上データがない
Geminiを呼び出さないfallback
```

では回数を消費しません。

### Guest prompt上限

公開Demoから送信されるAI promptが無制限に大きくならないよう、  
GuestのAI adviceでは対象Datasetの売上を集計したうえで上位商品数を制限しています。

商品名や数量についても送信前に再検証します。

AI APIはPOSTとして扱い、CSRF保護も適用しています。

</details>

<details>
<summary><strong>🚧 Guest Demoの公開防御を見る</strong></summary>

<br>

公開Demoでは、

```text
機能が正常に動く
```

だけではなく、

```text
大量アクセスされたら？
同時requestされたら？
上限を回避されたら？
```

という前提でも確認しています。

### Guest Session作成rate limit

Guest Session作成にはclient単位のrate limitを設定しています。

client識別では、生IPそのものをDBへ保存せず、  
HMAC-SHA256で匿名化したkeyを使用します。

```text
Client IP
↓
検証・正規化
↓
HMAC-SHA256
↓
匿名client key
```

rate limitの利用回数はGuest Dataset作成前に確保します。

そのため、後段でDataset作成に失敗した場合でも、  
確保済みの利用回数を戻して大量試行を許可することはしません。

設定不備・client情報不備・DB障害時は安全側へ倒し、Guest作成を拒否します。

### 有効Guest Dataset数

同時に存在できる有効Guest Datasetは既定値で最大10件です。

Guest開始時には、

```text
cleanup
↓
現在の有効Guest数を確認
↓
上限未満なら新規Dataset作成
```

という順で処理します。

PostgreSQLではadvisory lockを利用し、  
複数requestが同時に「まだ空きがある」と判断する競合を抑えています。

### 商品・POST上限

Guestでは、

```text
1 Datasetあたりの商品総数
最大30

1回のProduct POST
最大30件

1回のSales POST
最大30件
```

としています。

論理削除した商品もGuest Datasetの生涯商品数として数えるため、  
削除と再登録を繰り返して無制限にデータを増やすことを防ぎます。

既存Productの更新や論理削除自体は、新規商品枠を消費しません。

同時Product POSTについてもPostgreSQL上で上限を超えないことを確認しています。

</details>

<details>
<summary><strong>🔐 Admin認証・Session・rate limitを見る</strong></summary>

<br>

管理者側はFlask-Loginによる単一管理者方式です。

認証情報は環境変数から取得します。

```text
SECRET_KEY
ADMIN_USERNAME
ADMIN_PASSWORD_HASH
```

平文passwordをコード内へ保存せず、Werkzeugのpassword hashを利用します。

### Session fingerprint

ログイン時には現在の`ADMIN_PASSWORD_HASH`からfingerprintを生成し、Sessionへ保存します。

```text
ログイン時
↓
現在の認証設定からfingerprint生成
↓
Sessionへ保存
```

Session復元時には、

```text
現在の認証設定
↓
fingerprint生成
↓
Session内のfingerprintと比較
```

します。

次の場合は既存Sessionを認証済みとして扱いません。

```text
fingerprintが存在しない
fingerprintが一致しない
管理者設定が不足
password hashが無効
```

これにより、管理者password hash変更後に古いSessionが残り続ける状態を防ぎます。

### Admin login rate limit

管理者ログイン失敗には、

```text
5回 / 15分
```

のrate limitを設定しています。

```text
1〜5回目
HTTP 401

6回目以降
HTTP 429
```

上限到達中は、正しい認証情報を送信した場合でも429として扱います。

また、

```text
wrong username
wrong password
```

によって外部レスポンスを変えません。

Guest作成rate limitとは別のHMAC domain・counterを使用しています。

PostgreSQLでは、同一clientの、

```text
上限確認
↓
credential検証
↓
成功判定
↓
失敗counter更新
```

を直列化し、並行requestによるrate limitすり抜けも検証しています。

```text
    │
    └── Gemini API
```

AdminとGuestでは認証経路が異なります。

Product・DailySales・MaterialOrderItem・ShopMemo・Dashboard・AIなどの業務データを扱う場合は、  
現在のidentityから利用可能なDatasetをサーバー側で解決します。

### 2. 環境変数を作成

```bash
cp .env.example .env
```

主な環境変数は次のとおりです。

```env
LOCAL_DEVELOPMENT=true
GEMINI_API_KEY=
SECRET_KEY=
ADMIN_USERNAME=local-admin
ADMIN_PASSWORD_HASH=
GUEST_CREATION_RATE_LIMIT_MAX_ATTEMPTS=5
GUEST_CREATION_RATE_LIMIT_WINDOW_SECONDS=60
```

`LOCAL_DEVELOPMENT=true`は、手元のPCで直接Flaskへ接続するときだけ設定します。
このmodeではrate limit用IPに接続元の`remote_addr`を使い、HTTP開発用に
Session cookieの`Secure`属性を無効化します。

未設定や`true`以外の値ではLocal Development Modeになりません。
通常環境では従来どおり`CF-Connecting-IP`が必須で、`remote_addr`や
`X-Forwarded-For`へfallbackしません。

`SECRET_KEY`は値を画面へ表示せず、次のコマンドで`.env`へ保存できます。

```bash
python -c 'import secrets; from dotenv import set_key; set_key(".env", "SECRET_KEY", secrets.token_hex(32)); print("SECRET_KEYを.envへ保存しました。")'
```

`ADMIN_PASSWORD_HASH`には、平文passwordではなくWerkzeug互換hashを設定します。
次のコマンドはpasswordを非表示で2回入力し、hashを表示せず`.env`へ保存します。

```bash
python -c 'import getpass; from dotenv import set_key; from werkzeug.security import generate_password_hash; password = getpass.getpass("Local Admin password: "); confirmation = getpass.getpass("Confirm password: "); assert password and password == confirmation, "passwordが空、または一致しません。"; set_key(".env", "ADMIN_PASSWORD_HASH", generate_password_hash(password)); print("ADMIN_PASSWORD_HASHを.envへ保存しました。")'
```

`ADMIN_USERNAME`は`.env`内で任意のローカル用ユーザー名へ変更してください。
平文password、生成したhash、`SECRET_KEY`をGitへ追加しないでください。

Guest Session作成rate limitには、`.env.example`にある次のローカル用設定を
使用できます。

```text
GUEST_CREATION_RATE_LIMIT_MAX_ATTEMPTS
GUEST_CREATION_RATE_LIMIT_WINDOW_SECONDS
```

> [**⚠️ 注意**]
> `.env`にはAPIキー・SECRET_KEY・認証情報などの機密情報が含まれます。  
> GitHubなどの公開リポジトリへpushしないでください。
> `.env`は`.gitignore`と`.dockerignore`の対象です。

### 3. Docker Composeで起動

```bash
docker compose up --build
```

新規DBは自動migration・seedされず、schema不一致ならWebは起動しません。開発DBの準備は [保守手順](docs/startup-maintenance.md) を参照してください。

ブラウザからアクセスします。

```text
http://127.0.0.1:5000
```

### Dockerを使わない場合

依存関係をインストールします。

```bash
pip install -r requirements.txt
```

migrationを適用します。

```bash
flask db upgrade
```

Flaskを直接起動します。`python app.py`では、`config.py`を読み込む前に
repository直下の`.env`が読み込まれます。すでにOS側へ設定された環境変数は
`.env`で上書きされません。

```bash
python app.py
```

`DATABASE_URL`が設定されていない場合はSQLiteを使用します。
開発serverは`0.0.0.0:5000`で待ち受けるため、信頼できる同一LAN内では
`http://192.168.x.x:5000`のようにスマートフォンから確認できます。

### Phase 4 Guestスタッフ（開発中）

`GUEST_STAFF_ENABLED` は既定OFF。v3.2 Guestレジの有効な体験に限りスタッフ・シフトとホーム出勤予定を共通画面で利用します。仕込み・廃棄は今回まだGuest非公開です。公開は別承認です。

Guestスタッフの追加検証では正規Guest開始からAdmin共通CRUD契約、Admin/Guest ID越境、期限切れHTTP拒否を確認します。PostgreSQL cleanup試験には全主体のStaff/Shiftを含め、ロック競合・rollback後の保持も照合します。
