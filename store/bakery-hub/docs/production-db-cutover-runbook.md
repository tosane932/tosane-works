# PostgreSQL期限前の移行判断・当日チェックリスト（Phase 3E・未実施）

これは**将来の作業順序と停止基準**であり、新DBの作成、旧DB削除、復元、本番設定変更、料金変更の許可や実施記録ではない。正式レジはNO-GO。実作業には移行先、作業窓、費用、復元先への書込、切替について別途承認が必要。[最新の期限と選択肢](production-db-free-expiry-plan.md)、[G580取得コマンドと記録欄](g580-encrypted-db-backup.md)、[独立復元と読取照合](g580-restore-verification.md)を参照する。秘密の接続URL・パスワード・鍵・個人情報を記録しない。

## 事前に解消すべき技術的なSTOP

1. 現行 `Dockerfile` は起動のたびに `flask db upgrade && python seed_demo.py && gunicorn ...` を実行する。新レジ商品・レシピのみ存在し、旧ProductとDailySalesがないDBにはseedが旧デモ商品・売上を投入し得る。**新DBをWebへ接続する前に**、別PRで自動migration／自動seedを通常起動から分離する設計・テスト・デプロイを承認し、復元DBの正常起動で意図しない書込がないことを検証する。migration失敗後にseed/gunicornへ進まない現行 `&&` は保たれているが、先に完了したmigrationは後続seed失敗で巻き戻らない。mainは自動デプロイ有効なので、切替前のコードmergeと起動の時点も管理する。
2. 現行 `production_backup_guard.py restore-encrypted-approved` は復元前と復元直前の**両方で元DBへ接続する `preflight`** を呼ぶ。旧Freeが期限切れでアクセス不能なら、このコマンドでは新DBへ復元できない。期限切れ後の移行を選ぶなら、元DBに接続しない安全な**暗号化原本＋承認済み元DB識別記録に基づく復元専用経路**を別PRで用意し、隔離された合成PostgreSQL 18で空DB・別ホスト・SHA-256・復号・権限・失敗時rollback・誤接続拒否を検証する。既存ガードを迂回する即席コマンドは本手順に含めない。元DBが生きていても、新Freeを同時にactiveで作れるとは仮定しない。
3. Freeのactive DBは同一Workspaceに1つ。期限後は旧DBへ接続できず、旧DBを**先に削除すれば切戻し先そのものを失う**。旧DBを削除せず新Freeを作れる条件は未確認。Render管理画面で作成条件・停止時間を確定できない場合、削除や切替に進まない。有料継続・別事業者も含め移行先を決め直す。

## Gate 0｜事前承認・候補日（どれか不明ならSTOP）

- 記録上の期限は**2026-11-12 12:19:04 JST**。Render管理画面で作業直前の状態・期限を再確認し、期限より十分前に停止窓を確保。期限までの2〜3日ごとの取得は[G580の反復チェック](g580-encrypted-db-backup.md)に従う。
- 元DB `bakery-db-4`（`bakery_db_4`）とWeb `bakeryhub` の実効接続先を管理画面でホスト・DB名で照合。移行先DBの管理者・識別子・リージョン・PG major・TLS・容量・権限・作成条件・費用を別に記録。DB接続文字列そのものは書かない。
- 有料費用または旧DB削除が必要なら、それぞれ独立に明示承認。許容停止時間、失敗時の業務対応、保存世代、暗号文の独立コピー、USB復号鍵と予備鍵、端末一覧と未同期会計の担当者を確定。
- 上記のseed／migrationと期限後復元のブロッカーを解消し、合成試験を通す。切戻しの可否と、新DBに新たな書込が発生した後の差分反映方針を事前承認。

## Gate 1｜更新停止

- Admin・Guest・他の端末へ作業停止を案内し、商品・レシピ、旧日次売上、会計・返金、スタッフ・シフト、バックグラウンド同期を含む**全書込経路**を止めたことを担当者が確認する。見た目のメンテナンス案内だけで書込停止とは判定しない。
- スマホ・P10等すべての端末で、IndexedDBの未同期件数・元キー・金額・要確認案件を確認。DB dumpには含まれない。端末の再起動・クリア・強制再送をしない。未確認端末があれば切替STOP。
- 更新停止時刻、最後の成功書込、対象端末と担当者を個人情報なしで記録。停止前後に新しい書込があればGate 1をやり直す。

## Gate 2｜最終暗号化バックアップ

- 元DBがavailableかつWeb接続先一致、PG18クライアント、保存先700、鍵の別保管、空き容量を確認。[G580の `backup-encrypted` → `verify-encrypted` 手順](g580-encrypted-db-backup.md#5本番から直接暗号化して保存最終確認後)を**新しい一意名**で実施し、サイズ・権限600・SHA-256・完全復号・custom形式を記録。平文dumpは通常ディスクへ書かない。
- 別保存先へ暗号文のみをコピーし、ダウンロードしてSHA-256一致を確認。容量不足・エラー・鍵不一致ならSTOP。取得と復号だけで復元PASSとしない。
- 必要な隔離復元と[詳細照合](g580-restore-verification.md)を承認済みの独立・空DBで実行し、終了後の隔離DB消去・swap復帰を確認。10月21日分の実績を今回の最終取得に流用しない。
- 元DBの全表・重要集計の基準値を取得するなら**別途承認した読取範囲**で、確実な更新停止中に取得して時刻を記録。ダンプとの時点一致が立証できない場合は完全一致PASSにしない。

## Gate 3｜移行先を作成・再同定（別承認後）

- 移行先が元DBとは異なる指定先であること、PG major 18、TLS・接続制限・十分な空き容量・権限を確認。復元直前に新DB名・ホスト／サーバー識別子・空状態を再確認。**空でないDBへ上書きしない。**
- Admin／Guest Datasetは元DBから復元する対象であり、復元前の先行seedやデモ登録を認めない。通常Web起動で先にmigration・seedが走る設定ならSTOP。
- Freeの同時active数制限で新DBを用意できない場合、旧DBをその場で削除して進めない。Gate 0に戻り別案と切戻し不能を承認する。

## Gate 4｜復元・照合

- 承認済みの安全ガードと空DBへ暗号文から復元。元DBへ接続できないときは、上記の別PRで検証された復元経路が存在する場合に限る。`pg_restore`正常終了だけではGOにしない。
- 27表を固定期待値にせず、**最終dumpの実際の全テーブル**、件数、Admin／Guestの所有関係、旧商品、新レジ商品・写真・レシピ・材料、旧日次売上、会計・明細・返金、スタッフ・シフト、メモ、天気履歴、Alembic revision、FK/PK/UNIQUE/CHECK・トリガー・sequence・インデックス、主要参照の孤児件数を検査。日別売上や写真のハッシュは個人情報・バイト列を出さず集約値だけを扱う。
- 更新停止とdumpの同時点性が証明できない場合、後日の元DBと復元DBの差だけでPASS/FAILを決めない。差分の理由が不明、権限不足、制約異常、Dataset混在ならSTOP。復元失敗時は同じ汚れたDBへ再実行せず、新たに承認された空DBへ。

## Gate 5｜Web接続先切替判定（今回のPhaseでは実行禁止）

- Gate 0〜4の記録、seed／migrationの安全な起動試験、端末未同期の扱い、管理者の切替承認、旧DBと新DB双方の状態、切戻しの有効時間と差分データの扱いがすべて揃うまでSTOP。
- 接続先変更、プラン変更、デプロイはそれぞれ別承認。接続先変更後も書込はまだ再開しない。新DBに書込が一件でも生じたら、旧DBへ接続し直すだけではその書込を失う。書込停止を継続し差分の保全・再反映を承認できなければ切戻しSTOP。
- 旧DBが利用可能かつ保持され、切替後に新DB書込がない（または完全に保全・再反映できる）間だけ、元の接続設定への切戻しを候補にできる。期限切れ・削除済みなら旧DBへ戻れず、暗号文から別DBへ復元する復旧計画が必要。

## Gate 6｜読取確認・業務再開

- Webが指定DBを使うことを秘密値を出さず照合し、Admin認証・Guest分離、商品一覧・日次売上・ダッシュボード・レシピ・シフトを読取確認。必要な書込試験は別途承認し、本番データを無断で変更しない。
- 端末ごとの未同期・要確認件数と元キーを保存したままサーバー側の確定件数・金額を照合。元キーによる二重送信防止と既存の認証・同期手順を再確認し、承認前に再送しない。
- 照合と切戻し条件を再評価してから更新再開を判断。新DBの世代別暗号化バックアップ間隔と隔離復元試験を再設定する。DB移行が成功しても正式レジ公開は独立の審査で**NO-GO**を維持する。
