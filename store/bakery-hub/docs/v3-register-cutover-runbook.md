# Bakery Hub v3.0 正式レジ切替手順書（Phase 6）

最終更新：2026-10-17。**現時点の判定は NO-GO。本書はPhase 7で管理者が実施する作業の準備であり、Phase 6で本番DB・Render・切替日は変更しない。** 正式レジの初期利用者はAdminのみ。Guest Demo、Admin非保存デモ、旧日次売上履歴を残す。

## 記録と停止の原則

- 実施担当・確認担当、作業日時（JST）、対象Dataset、リリースSHA、DB revision、端末台帳版、監査結果、承認者、証拠の保管先を作業記録に残す。秘密情報・PIN・会計の個人情報をチケットや画面写真に記載しない。
- **全端末・全未同期記録を確認できない、復元試験が不成功、監査にblockerがある、旧ワーカーが書ける、または実機試験が未完了なら切替しない。** チェックボックスやサーバーDBだけでは端末のIndexedDBを証明できない。
- 保存前の端末会計（IndexedDB）、サーバー保全済みの復旧案件、確定済みRegisterTransactionを別々に数える。保留・要確認は確定売上に含めない。未同期キューを消して帳尻を合わせない。
- 旧DailySalesの履歴はそのまま維持する。切替日より前は旧、切替日以降は確定した新レジ会計のみを集計する。旧商品には販売時単価の完全な履歴がないため、旧期間の商品別金額は従来の推計上の制約がある。

### 確認済みの技術的境界

Phase 5C終了時の記録は全pytest 1,329 passed / 44 skipped、JavaScript 30 passed、ヘッドレスChromium E2E 6 passed、隔離PostgreSQL関連43 passed、GitHub Actions成功。これらは**当時のコード・検証環境の結果**で、実端末や本番DBでの合格を意味しない。Phase 6では、切替監査が旧新同日重複、切替以降の旧行、切替以前の新会計、ヘッダーと明細の不一致、標準18商品の欠損・無効、販売可能商品の欠如、未解決復旧案件をblockerにすることをコードで再確認した。無効商品、同名別商品、500円超の旧商品、レシピ未対応は各項目の管理者理由を要求する。全端末確認はアプリで自動検証できない。

`confirm_cutover()`はAdminの認可済みDataset行をロックし、同じDB transaction内で既存切替日と監査を再確認する。blockerまたは必要な確認記録の欠落はrollback。同じ日への再実行は安全に扱い、異なる日への上書きは禁止。旧日次入力POSTと通常・オフライン・例外復旧保存は同じDataset境界の排他を用いる。会計キーはDataset内一意で、異なる内容の同じキーは拒否する。返金は負の明細・合計として保存する。価格・名称は会計時のスナップショットを保持する。切替画面のGET事前監査だけで切替日を確定してはならない。

オフラインでは端末へのIndexedDB書込完了後に次の会計へ進む。サーバー確定は別状態。PINで暗号化した商品・端末許可と専用Service Workerシェルを使い、認証済みHTML、Cookie、API応答を無差別にキャッシュしない。期限付きのAdmin端末許可と署名付き商品版、元のsubmission_key・営業日・価格を同期時に検査する。翌営業日の承認済み会計は限定された期限・金額・件数内で元の日へ同期できる。不一致、失効、認証切れは元の記録を保持して要確認にする。端末時計は会計日時の独立証明にならない。端末故障またはブラウザデータ消去で、端末にしか存在しなかった会計は自動復元できない。

## バックアップ、隔離復元、migration

本番操作はPhase 7で別途明示承認を得て行う。Phase 6では本番DBの版、接続方法、バックアップ権限、Renderの管理バックアップ有無・保持期限・利用可能な復元先を未確認とする。以下は**実行例**で、対象と接続先を二人で照合してから使う。接続文字列やパスワードをコマンド行、ログ、チケットに出さない。libpqの保護されたservice/パスワード設定を使用する。PostgreSQL公式の [pg_dump](https://www.postgresql.org/docs/current/app-pgdump.html) と [pg_restore](https://www.postgresql.org/docs/current/app-pgrestore.html) に従い、サーバーとクライアントの版の互換性も確認する。

1. レジ保存を開く前に書込の停止窓と担当者を確定し、旧商品・旧売上・新会計・復旧案件を含む**DB全体**を一貫したスナップショットで取得する。アクセス権を限定した保存先を指定し、保管・廃棄の期限を記録する。サービスの自動バックアップを使う場合も実体と復元方法を確認する。
2. 例（権限保護されたシェルで、service名と保存先は承認済みの実値へ置換する）。`umask 077`、`pg_dump --dbname='service=approved_source' --format=custom --file=/protected/backup/precutover.dump`、`sha256sum /protected/backup/precutover.dump`、`pg_restore --list /protected/backup/precutover.dump`。終了コード、サイズ、照合値、取得日時、対象DB識別子を記録する。`--list`だけでは復元可能性を証明しない。
3. **本番とは別の空の隔離DB**を承認した管理者が作成し、ネットワークと権限を隔離する。対象が空であることを確認後、`pg_restore --dbname='service=approved_restore_target' --no-owner --no-acl --exit-on-error /protected/backup/precutover.dump` を実行する。**本番を復元先に指定しない。** 終了コード、revision、全関連テーブル件数、代表日の合計・FK/UNIQUE/CHECK、認可境界を照合する。復元DBを公開アプリに接続しない。
4. ロールバック練習は復元先と検証データで行い、復元を本番で行う条件・責任者・作業停止窓を別途決める。新会計が一件でも発生した後、切替前のダンプを本番に上書きしてはいけない。復元以降の確定会計と端末キューの照合なしには売上を復元できない。

対象表には `datasets`、`products`、`daily_sales`、`register_products`、`register_price_history`、`register_prep_links`、`register_cutovers`、`register_cutover_approvals`、`register_transactions`、`register_transaction_lines`、`register_recovery_cases`、`register_recovery_lines`、`register_recovery_events`、`register_offline_permits` と `alembic_version` を含める（全DBバックアップなので他の関連表も含まれる）。現行mainの**単一headは `a3c9d7e5f102`**。Phase 5C区間は `da5c1e7f9042` → `eb6c2f8a4130` → `f5a17b3e2c09` → `a3c9d7e5f102`。本番の出発revisionは未確認であり、途中のrevisionを推測して飛ばさない。旧売上・既存会計を保全するupgradeと、データがあるときのdowngrade拒否を隔離DBで確認する。複合Dataset FK、一意キー、金額・返金CHECK、監査追記制約と行数を検証する。**データありのdown migrationを復旧手段にしない。**

`Dockerfile` のCMDには `flask db upgrade && python seed_demo.py && gunicorn ...` がある。実デプロイでこのCMDが使用されるか、別の開始コマンドか、複数ワーカーが同時にmigrationを試みるかはPhase 7で確認する。バックアップ検証後、単一の承認済みmigration実行経路を決め、新機能をOFFのままupgradeとrevision・旧件数を照合する。旧版がまだ旧日次POSTを処理できる間は**切替日を確定しない**。

### 読取監査の記録欄

本番の読取権限だけで、接続先識別子、`alembic_version`、旧商品/旧売上件数と旧売上最終日、レジ商品/価格履歴、切替日/承認、新会計/明細、復旧案件/イベント、端末許可、仕込み対応の各件数を記録する。Datasetをログイン主体のAdmin IDと照合する。管理者用 `/register/readiness?date=YYYY-MM-DD` の監査結果、同日重複、ヘッダー・明細不一致、旧新境界、標準商品18品と価格、未解決案件、review項目と対応理由を証拠として保存する。監査画面は端末キューを数えられない。商品別・日/月/年・返金・0円と未記録・ホーム・AI入力・仕込み参考の出力も切替前後で照合する。実Gemini APIはこの監査では呼ばない。

## 機能フラグ台帳（現在のコード上の既定値は全てfalse）

`true` は環境変数で明示したときだけ有効。本番では `LOCAL_DEVELOPMENT` を有効化せず、Secure Cookieを維持する。表は**コード上の効果**で、本番の実設定値を意味しない。Guestの正式会計は `PRODUCTION` のAdmin制限で拒否される。旧日次入力はフラグだけで閉じず、切替日以降のPOSTがDatasetロック下で拒否される。

| フラグ | 追加条件とAdminでの効果 | Guest・旧入力への影響／OFF時 |
|---|---|---|
| `REGISTER_V3_PRODUCTION_ENABLED` | PREVIEW/SAVE/集計/商品フラグの本番ゲート、Adminだけ正式機能 | Guest正式会計拒否。OFFでは本番側の正式ゲートを閉じる |
| `REGISTER_V3_CUTOVER_ENABLED` | READINESS+RECOVERYが揃うとAdminの切替確定POSTを許可 | Guest不可。OFFは確定POST 404。既存切替行は残る |
| `REGISTER_V3_PREVIEW_ENABLED` | PRODUCTIONと切替日到来でAdmin正式画面 | OFFは画面404。これだけでは保存できない |
| `REGISTER_V3_SAVE_ENABLED` | PRODUCTION、Admin、切替日・保存ルールの検証で会計POST | OFFは新規正式保存を止める。旧POSTを再開しない |
| `REGISTER_V3_AGGREGATION_ENABLED` | PRODUCTION下で切替境界の新旧集計を表示 | OFFは新集計の表示ゲートを閉じる。売上行は残る |
| `REGISTER_V3_PRODUCTS_PREVIEW_ENABLED` | PRODUCTION下でAdminの商品管理表示 | OFFは管理画面不可。正式レジ公開とは独立 |
| `REGISTER_V3_PRODUCTS_WRITE_ENABLED` | 商品管理表示との組合せでAdmin商品書込 | OFFは商品管理書込停止。Guestへは開かない |
| `REGISTER_V3_RECOVERY_ENABLED` | Adminの案件管理・切替POST条件の一部 | OFFは復旧操作不可。保全済み案件は残す |
| `REGISTER_V3_OFFLINE_MODE_ENABLED` | PRODUCTION+PREVIEW+SAVE+切替済みAdminで準備・同期 | OFFは新規オフライン操作停止。端末キューは保持 |
| `REGISTER_V3_READINESS_ENABLED` | Admin監査画面、切替POSTの前提 | OFFは監査画面404。既存切替行は残る |
| `REGISTER_V3_PUBLIC_DEMO_ENABLED` | Admin非保存練習、正式フラグと独立 | Guestには開かない。Phase 7でも既存設定を維持 |

本番有効化の順番は**migration・復元検証 → READINESSで読取監査 → 必要なRECOVERY調査 → PRODUCTIONとPRODUCTS_PREVIEW/WRITEで商品確認 → 端末・ワーカー・バックアップのゲート → CUTOVERを短時間だけ開いて明示承認 → CUTOVERを閉じる → PREVIEW/AGGREGATIONを照合 → OFFLINE_MODEの準備 → SAVEを最後に開く**。切替日を決めた時点で旧POSTは閉じ、SAVEを閉じても旧POSTを再開しない。OFFLINE_MODEはSAVE前には新規準備できないので、端末準備はSAVE有効化後、正式営業開始前の管理された時間帯に行う。公開導線と初回営業開始を監視する。フラグの変更ごとにワーカーが同じ値を使うことを確認し、PUBLIC_DEMOは変更しない。機能フラグを一括ONにしない。

## Phase 7 実行順（各段階で記録し、失敗なら次に進まない）

1. **環境確定**：対象サービスとDB、リリースSHA、ワーカー数・各版、開始コマンド、自動migration、Cookie設定、全フラグ、本番revisionを読み取る。新旧ワーカー混在の終了条件を決め、旧版が旧POSTを受ける状態で切替を行わない。作業窓・連絡手段・管理者承認を記録。
2. **バックアップと復元**：書込状態を調整し全DBをバックアップ。アーカイブ一覧・ハッシュだけでなく、隔離先への復元と件数・revision・制約照合を合格させる。失敗なら中止。
3. **migration**：正式フラグOFF、単一の承認済み経路で適用。headと各表・制約、既存行数・代表日の旧売上を照合する。実行経路とワーカー再起動を監視。
4. **事前監査**：READINESSで予定日を指定して読取監査。標準18品、独自商品とレシピ、名称・価格、旧新境界、現金/帳簿、復旧案件、全端末照合票、実機結果を確認。blocker、未確認端末、未解決会計、未承認reviewが残れば中止。
5. **切替確定**：旧書込を受ける旧版ワーカーが完全に排除されたと確認。管理者が日付・理由・端末台帳・バックアップ確認・review別理由を明示入力し、確定POSTに再監査させる。切替行と承認行を読み戻す。別日付への変更や見かけ上の巻き戻しは禁止。
6. **正式導線**：必要なフラグを段階的に確認し、SAVEは最後。旧GETで履歴を閲覧でき、切替日以降の旧POSTは拒否、新POSTはAdmin・正しいDataset・日付でのみ成功することを確認。**本番でダミー会計を作らない。** 許可された実売上で運用確認するか、隔離先でのみテストする。
7. **監視と照合**：通常会計、返金、同一キーの再照合、端末保存と確定の区別、翌日同期、Dashboardの日/月/年・商品別、ホーム、AIへの入力、仕込み参考を実売上・現金日報と照合。異常を見つけたら以下の停止手順へ。

## 障害時の停止・復旧

| 発生段階・例 | 直ちに行うこと | 再開条件 |
|---|---|---|
| migration前・バックアップ失敗 | 正式フラグOFFを維持、既存日次運用を継続。原因とDB revisionを記録 | 隔離復元を実際に合格させる |
| migration後・切替前の制約/ワーカー異常 | 新機能OFF、書込窓を安全に維持、revisionと行数を調査 | 旧日次運用の整合と新版の完全デプロイを確認。データありdowngradeをしない |
| 切替後・新会計なし | SAVEを閉じ、旧POSTの遮断を継続、切替行・承認・端末キューを保全 | 管理者が監査し、既存切替日を維持した安全な再開を承認 |
| 新会計保存後の二重計上・価格/集計不一致・認可事故 | SAVEを閉じ、必要ならOFFLINE_MODEも閉じて新規同期を止める。確定行、ログ、端末原本と現金証拠を保全 | 同一キー・明細・Dataset・旧行との関係を調査し、差異の処置を別途承認。過去ダンプの安易な上書き禁止 |
| 通信断、未同期キュー、古いService Worker、端末故障 | 元キューを削除しない。端末とサーバーのキーを照合し、復旧案件と現金日報を調査。保存不能なら会計完了を止める | 認証再検証・端末許可・版・証拠を確認。端末のみの失われた記録は自動復元不可 |

緊急停止はまず `REGISTER_V3_SAVE_ENABLED=false`（必要ならオフライン同期も停止）を承認済みの手順で反映し、全ワーカーへの反映と結果を確認する。**切替後に旧DailySalesの書込を無条件に戻さない。切替行や確定会計を削除・巻き戻さない。** 調査結果と現金・帳簿との差額を管理者が確認してから復旧方針を決める。ログアウト・端末紛失では許可を失効させ、オンライン再接続までオフライン失効を即時反映できない制約を考慮する。
