## 商品管理統合・端末別レジ表示（2026-10-20更新）

正式レジの本番切替は引き続き **NO-GO**。この変更は作業ブランチの実装であり、本番DB・Render設定・機能フラグは変更しない。以下を現行仕様とし、後述のPhase別記録に残る「500円上限」「18品必須」「独自商品別枠」「画像アップロードなし」は当時の実装記録として読む。

- Adminの商品管理フラグが有効な環境では、`/products` の「商品一覧」を入口にする。旧 `/register/products` と旧月次登録 `/` のGETは商品一覧へ案内する。旧月次登録は一覧内の履歴用リンク（`/?legacy=1`）から参照可能。Guestの月次登録・日次売上入力は変更しない。フラグ既定OFFの環境は従来画面を維持する。
- 正本は既存の `RegisterProduct`。パンの種類（8種類）と商品分類（定番・季節もの・特別商品）、写真、価格、`is_active`を同じIDで管理する。既存行の分類は推測せず「その他・定番」を初期値とする。必要な商品を店主が分類する。
- 新規登録・編集は同じ写真中心のフォーム。承認済み画像、写真ファイル、スマホ撮影を受け付け、名前・価格・分類とともに確認ダイアログを表示する。写真なしなら文字タイルを維持する。
- 写真は既存 `catalog_repository.validate_image()` で拡張子・MIME・実画像・10MiB上限・画素数・単一フレームを検証し、メタデータを除いて500KiB以下のWebPへ変換。`RegisterProduct.photo_webp` に保存し、Renderの一時ファイルへ置かない。既存承認画像は `image_key` のまま使い、新規写真と同時に二重保持しない。認証済みの所有Datasetだけが写真URLを読める。写真の保存量は商品数に比例するため、DB容量とバックアップ容量も運用時に確認する。
- 終売は `is_active=False`。一覧下部に残し、新規レジのカタログから除く。同じID・写真・分類・価格履歴・仕込み対応・過去売上のまま、価格確認後に再開できる。通常UIに物理削除はない。
- 18商品は初期候補。管理画面やAdminレジのGETでは生成しない。確認付きPOSTだけが不足候補を追加する。既存品の変更や終売解除はしない。内部 `template_key` とGuest開発プレビューの初期化互換性は維持する。18品すべての登録・販売を切替条件としない。
- 新規登録はUUID送信キーと内容digest（写真・分類も含む）で再送を識別する。更新・終売・再開は署名したDataset・商品ID・版番号、Datasetロック、CSRFで保護する。同一更新の直後の再送は許容し、別編集や終売→再開後の古いフォームは409で拒否する。価格変更時だけ `RegisterPriceHistory` に追記する。
- 商品単価は整数 **0〜100,000円**。商品、価格履歴、会計明細、復旧明細、同期時の表示価格照合に同じ上限を適用。数量±50・1会計50商品・会計合計の既存上限は維持する。0円合計会計は保存不可。既存の承認価格資料や実売価は推測で変更しない。
- レジはスマホ幅（850px以下）で全商品を2列・縦スクロール表示し、合計付き下部固定「会計へ」からキーパッドへ移動して元の商品位置へ戻る。851px以上は実際の表示高と操作方式から、タッチ主体は2行、マウス主体は読みやすい寸法を保てる2〜4行とし、正方形タイルを商品領域だけ横スクロールする。内部グループは最大12商品、未登録枠は最後の縦1列を揃える分だけ（2行なら最大1枠、0商品は0枠）。空き枠は商品ID・操作・入力・フォーカスを持たず、aria-hiddenで読み上げから除く。写真全体・名前2行・価格・48pxタッチ領域の−と数量入力・タイル全面タップ＋1を維持する。横長画面のテンキーは4段・52〜60px、会計完了は56px。ヘッダー・通知・会計部を実測して1画面へ調整し、収まらない低い画面や文字拡大では重要操作を隠さず本文縦スクロールへ退避する。数量操作で一覧を再構築せず、回転・行数変更でも商品DOMと会計状態を保持する。
- 横長画面は長文説明帯を練習用・未保存／正式・開発用・未公開・保存停止等の状態バッジへ集約。ヘッダー36px、戻る・前次の見た目32px／タッチ44pxを両立。空の明細案内を重複表示せず、実際の明細量だけを使い、残り高さを内部スクロールの上限にする。合計・お釣りの罫線と余白を削り、預りラベルと表示欄を同じ行にする。未同期・保存失敗・認証異常は隠さず、通知の行間と余白を圧縮する。資産trim-6と専用SWのv6キャッシュへ更新し、旧資産・IndexedDB・元会計は削除しない。
- タブレットの右会計は明細だけがスクロールし、合計・預り・お釣り・完了を常時操作できる。ヘッダー・説明を小さくし、商品見出しの横に前後操作を配置する。表示専用register_layout.jsが実際の要素高と可視画面高を測り、収まるときだけ1画面へ配置する。低い画面・文字拡大・長い警告は通常の縦スクロールへ戻し、操作をoverflowで隠さない。端末準備・保存照会はヘッダーから開くダイアログへ移し、要確認・失敗・同期状態の通知と破棄確認を維持する。
- `register_cash_pad.js`は0〜9・00・C（全消去）・末尾1桁削除を提供する。金額は円単位・桁区切りで表示し、入力欄やソフトキーボードへの操作は不要。キーパッド内ではPCの数字・Backspace・Delete/Cも使える。先頭ゼロを正規化し、整数0〜1,000,000,000円を受け付け、上限超過は元入力を保持して通知する。既存inputイベントを経由して計算・下書きを更新する。会計完了後はリセット、返金では預り操作を隠し、処理中やデモ完了後はキーパッドを無効にする。
- スクロール処理は会計状態に触れない。数量・預り・釣銭・返金を維持する。非保存デモも同じスクロールとキーパッドを使うが、保存用JSを読まない。オフラインシェルはv4の同じ版のキャッシュから表示制御・キーパッドを読み込み、旧キャッシュや未同期キューは削除しない。資産URLにも同じ版番号を付け、旧Workerが更新待ちの場合は準備完了にせず、全レジタブを閉じて再準備するよう案内する。強制activateはしない。
- オフライン準備時は写真をdata URLとして既存の暗号化カタログ内に含める。認証付き写真をService Workerの公開画像キャッシュへ追加しない。元会計の価格・スナップショット・営業日・送信キー・未同期記録をページ操作やマスタ変更で更新しない。既存の署名商品版によるオフライン受入、通常会計の価格差・要確認・再送防止を維持する。オフライン自動受入は既存の1会計50,000円までを維持し、それを超える会計は元記録を残して管理者確認へ回す。
- 旧 `Product`・`DailySales` に自動移行・同名統合・金額更新・削除はしない。旧商品のコピーは明示確認した別IDとして登録し、売上自体はコピーしない。既存の `RegisterPrepLink` と標準品のレシピキーは変えない。

### スキーマとマージ前の停止条件

単一head `b6d2e9f4a107`、親 `a3c9d7e5f102`。既存表に `bread_kind`・`product_class`・`photo_webp`・`revision` を追加し、4表5価格制約を拡張する。旧Product・DailySalesと既存明細の値は変更しない。SQLiteの表再構築後は価格履歴・復旧明細の追記専用トリガーを再設定する。downgradeは新分類・写真・版番号・500円超の価格、またはレジ証拠行が存在すればDDL前に拒否する。データを削除してdowngradeしない。

**Dockerfileは起動時に `flask db upgrade` を実行する。** mainの自動デプロイが有効な場合、マージは本番migrationにつながり得る。管理フラグがOFFでもスキーマ変更は実行されるため、マージ前に本番バックアップ・別DBへの復元・稼働revision・旧ワーカー停止・メンテナンス方法・DB容量を確認し、適用の明示許可を得る。今回の作業では本番適用・切替日の確定・公開を行わない。


## 1. 目的と確定仕様

判断基準は「誰でも使いやすいシステム。裏側ではしっかり仕事をするシステム」。スマートフォンと横向きタブレットで、説明なしに商品写真を選び、間違いを訂正し、会計できることを目指す。保存、認可、金額検証、競合防止はサーバーとDBが担う。

| 項目 | 確定した方向 |
| --- | --- |
| 入力単位 | 従来の商品・日付別の一括入力を撤廃し、お客さん1会計ずつ記録。サイドメニューは「レジ会計」から専用画面へ直行。Admin/Guest共通。店長・販売員のモード選択なし。 |
| 会計操作 | 商品写真をタッチして＋1、商品・数量・合計を確認、お預かりを入力、お釣りを表示し、明示的に「会計完了」を押す。Phase 2Bからは**IndexedDBへの原子的な保存成功後**に次の会計へ進み、DBへの同期は別状態として表示する。レジ締め・営業終了ボタンなし。 |
| 商品 | 標準18種類をすべて表示し、独自商品を追加。標準品を使うための毎月の登録作業は不要。画像のない独自商品も名前・価格の大きなタイルとして使える。 |
| 数量 | タイルのタッチで＋1、左側の明確な−で減算。数量を大きく表示。1商品・1会計につき −50〜＋50 個。直接数量入力も用意。0から負へ移る際には返金確認。 |
| 返金 | 専用ページと元顧客への紐付けなし。負の会計を保存し、通常販売とDBで識別。返金も会計件数および平均会計額の分母・分子に含む。在庫復元なし。例の660＋720−220＋840＝2,000円、4件、平均500円。 |
| 戻る | 体験版レジ左上に「← 戻る」。入力中は「入力中の会計があります。保存せずに戻りますか？」と「会計を続ける／破棄して戻る」。未入力は確認不要。「※ 実店舗でレジ専用運用する際は、『戻る』ボタンは表示されません。」と案内する予定。 |
| 商品管理 | 商品登録をレジ利用の前提にしない。独自商品の新規登録は名前・価格を先に扱い、Admin/Guestとも画像アップロード必須にしない。後から商品一覧の編集・テンプレート画像選択を可能にする。 |
| 対象外 | 電子決済、レシート印刷、売切表示、在庫管理、レジ締め、実店舗用販売員ログインの実装。 |

### UIの骨格

- タブレット横向きは左側にスクロール可能な商品タイル群、右側に常時見える会計明細・合計・お預かり／お釣り・会計完了。スマホはタイルと明細を読みやすい縦構成にする。18品を**表示対象**とし、狭い画面に全品を無理に同時表示しない。
- タイルは画像の有無にかかわらず、名前、単価、大きな選択数量、＋のタッチ領域と独立した−ボタンを持つ。−の誤タッチを避ける配置・押下領域、色以外の符号と「返金」表示を用いる。
- 金額欄は「合計」「お預かり」「お釣り」を別ラベルで表示。返金時の金銭授受表示は後述の未決定事項。操作途中の戻る・画面遷移だけを必要最小限で確認し、会計完了は必ず店員の明示操作とする。
- 保存中は会計完了を無効化して状態を表示。ただしこれは補助策で、DBで同時POSTを防ぐ。成功応答を受けたときだけ新しい会計キーで次の入力へ進む。失敗時は入力を保持して再試行可能にする。

## 3. 推奨するDB構成

**推奨: 会計ヘッダー＋会計明細を新設し、`DailySales`は旧実績として読み取り専用で残す。** 新しい会計を`DailySales`へ複写しない。日次合算が必要なら、後述の共通集計層で二系統を一度ずつ足す。集計キャッシュを追加するのは性能測定後とする。

| 方式 | 利点 | 問題／判断 |
| --- | --- | --- |
| 会計テーブル＋明細 | 1件の境界、返金、時点単価、再送防止を表せる | 採用。新規集計の追加は必要。 |
| 会計を保存し`DailySales`にも加算 | 既存グラフを一部流用できる | 会計と日次行が二重の正本になり、再試行・返品・再集計で不一致や二重計上。採用しない。 |
| 旧`DailySales`を残し新会計と統合集計 | 既存行を無改変で守れる | 採用。Dataset・営業日の排他的な切替を必須とする。 |

提案する新テーブルと主要制約（名前は実装Phaseで確定する）。金額は円の整数、時刻はUTC aware、営業日はAsia/Tokyoの日付とし、ブラウザの時刻・価格・合計を正本としない。

| テーブル | カラムと制約案 |

### Phase 1Aのmigration順序とデータ保全

現行のAlembicは直列のrevisionで、調査時の単一headは`e2a7c4d9b105`。同revisionの`prep_ingredients`も`(recipe_id,dataset_id)`の複合FKを親テーブル作成後に定義している。Phase 1Aの4表は互いにFKで依存するため、**同一の追加migrationにまとめるのが合理的**。次のmigrationの`down_revision`は着手時のheadを再確認して指定し、`models.py`の定義と手書きDDLを照合する。DBが本番でどのrevisionかは未確認であり、適用は本Phase 0.1の対象外。

1. `register_products`（親は既存`datasets`）を作り、PKの`id`に加えて複合FKの参照先となる`UNIQUE(id,dataset_id)`、`UNIQUE(dataset_id,template_key)`、名前の空白除外・新レジ価格`0 <= price_yen <= 500`のCHECKを定義する。価格の刻みと0円商品の販売可否は未決定なのでDBで狭めない。
2. `register_cutovers`（`dataset_id`がPKかつ`datasets.id`へのFK）を作る。**Phase 1Aでは切替行を挿入しない**。初回切替日と旧売上行の有無を運用前に確認する。DBのCHECKだけで旧売上・新会計の日付重複は防げないため、保存経路と旧POSTの遮断も必要。
3. `register_transactions`を作り、`dataset_id`を`datasets.id`に結ぶ。`register_cutovers`へのFKは張らず、切替行の存在・`business_date >= first_register_date`は保存サービスで同一transaction内に検証する。`UNIQUE(id,dataset_id)`と`UNIQUE(dataset_id,submission_key)`を定義し、販売／返金の区分、合計の正負、預かり・お釣りの組合せをCHECKで制限する。切替日以降にしか新会計を記録できないことはCHECKやDataset FKだけでは保証できず、Phase 2Aの保存テストで確認する。
4. `register_transaction_lines`を作り、`(transaction_id,dataset_id)`から会計へ、`(register_product_id,dataset_id)`から商品へ複合FKで結ぶ。全FK列をNOT NULLとし、`UNIQUE(transaction_id,register_product_id)`、`quantity BETWEEN -50 AND 50 AND quantity <> 0`、単価の非負・安全な整数範囲と`line_total_yen = unit_price_yen * quantity`のCHECKを置く。同じ会計内で販売と返金を混在させない推奨案はアプリの明細検証でも守る。

明細の`dataset_id`は、会計と商品が**同じDataset**に属することをDBで保証するために必要。FK参照先の複合UNIQUEと子のNOT NULLが揃わなければこの保証は成立しない。各表のDataset FK・会計明細のFKは`RESTRICT`相当を基本とし、Admin商品と会計履歴の物理削除を防ぐ。Guest期限切れ時だけ、認可済み対象Guestの明細→会計→レジ商品→切替行→旧売上→旧商品→Datasetを明示的に消す。独立したGuestへの影響と削除途中の失敗時rollbackを検証する。FKの多経路cascade任せにはしない。

Phase 1Aでは0円会計をDBで表現できる余地を残す。実際の会計保存可否と価格の刻みは後続サービスで確定する。追加migrationの`upgrade`は空の4表・制約・索引のみ作成し、**既存の`products`、`daily_sales`、`datasets`の構造・行に触れない**。`downgrade`は明細→会計→切替→商品という逆順で表を落とすが、4表のいずれかに行があればデータ消失を防ぐため明示的に停止する。Phase 1B以降にデータが入った環境では通常のdowngradeを安全な復旧手段と見なさない。SQLiteでFK有効（`PRAGMA foreign_keys=ON`）の接続、PostgreSQLでFK・CHECK・一意制約の適用、両DBでupgrade→空表のみdowngrade、行のあるdowngrade拒否をテストする。

実装した会計合計・お預かり・お釣りのDB上限は安全のため絶対値10億円とし、販売件数の業務上限ではない。商品明細の合計と会計ヘッダーの合計が一致すること、Guest利用件数、営業日とUTC時刻の対応は後続の保存サービスで原子的に検証する。

### 保存と二重登録の防止

1. 画面は**会計を開始するとき**に予測不能な`submission_key`を発行し、失敗／通信切断後の再送でも同じキーを保持する。次の会計には新キーを発行する。CSRFトークンとは別物。
2. POST時にログイン主体のDatasetを取得。Guestは**同じDB transaction内**でDataset行をロックし、期限と利用上限を再確認する。キーと生の入力から正規化した商品ID／数量／預かり／返金確認等のダイジェストを求め、**先に既存キーを照会**する。同一入力の再送は、初回保存後に商品価格・有効状態が変わっていても元の会計を返す。異なる入力なら409。新規キーだけ、入力の商品IDをそのDatasetの有効なレジ商品から引き直し、重複ID・0・範囲外・行数超過・巨大ボディを拒否する。単価・明細金額・合計・お釣りはサーバーで再計算。クライアント送信金額を信用しない。
3. ヘッダーにダイジェストを記録し、全明細とともに**一回のDB transaction**で保存。`UNIQUE(dataset_id,submission_key)`が二重タップ・並行POSTの最終防壁となる。ダイジェストにはサーバーが後から変え得る商品価格を含めない。
4. 同じキーの再送でダイジェストも同一なら、既存会計を返して「保存済み」を確認可能にする。同じキーで異なる内容は409として新規保存しない。ユニーク競合後は必ずrollbackして別transactionで既存行を読み直す。通信切断時も保存状態の照会または同一キーの安全な再送で解決し、新キーを自動生成して重複会計にしない。
5. DB例外はrollbackし、入力内容を保持。保存成功の確証が得られるまで「次の会計」に進まない。PostgreSQLでは行ロック／一意制約、SQLiteでは一意制約に加え書込直列化・busy時の失敗処理を検証する。

UIの「0から負へ」の確認を飛ばす直接POSTにも備え、負数の会計にはサーバーが検証できる明示的な返金確認値を要求する。確認値はユーザー意思の再確認であり、認可・金額検証の代わりではない。

### Phase 2Aの保存サービスと将来のオフライン同期

`register_service.py`の`save_register_transaction(dataset, *, submission_key, kind, items, received_yen, refund_confirmed)`は認可済みDatasetと`(商品ID, 数量)`の列を受け、UTCのサーバー時刻からAsia/Tokyoの営業日を決める。DB上の有効商品をDatasetで絞り、PostgreSQLでは商品行もロックして、名称・単価・明細金額を同一transactionで固定する。`id`はDB内部のUUID、`submission_key`は会計開始時に端末が一度発行して再送でも保持するUUIDであり、両者を混同しない。ダイジェストは商品の並びを正規化したID・数量、販売／返金、お預かり、返金確認から作る。商品名・現行単価は含めない。同じキーと内容は以前の会計を返し、異なる内容は競合として拒否する。ヘッダーと明細は一括commitし、例外時はrollbackする。端末が応答を失っても、**同じキーで再送**すればDBに保存された結果を確認できる。ただし保存前に通信が切れて再送された時は、その時点の価格で初回確定するため、画面側には確認・差額提示が必要になる。

この段階のサービスはオンライン確定のみを扱う。切替行なし・切替日前・同日の旧`DailySales`ありの場合は新規保存を拒否し、旧テーブルへ複写しない。GuestはDatasetロック後に期限と会計件数上限（暫定1,000件）を確認する。1POSTは最大50明細、正規化データ16 KiB、お預かり上限10億円。0円会計と同一会計の販売／返金混在は**暫定的にサービス層で拒否**し、商品単価0円のDB登録、価格の刻み、混在時の正式ルールは未決定のまま。営業日ごとの通し「お客様番号」は現行UUIDから推定しない。必要になれば別migrationでDataset・営業日・表示番号の一意制約とロック下の採番を追加する。返金も1会計として数え、オフライン到着順と実会計順が異なる場合の表示順もその時点で決める。

オフライン会計は後続Phaseで端末内の永続キューを設計する。実会計時刻とサーバー同期時刻を区別して保存する追加カラム、時計改変への対策、価格表の版と同期時の価格差分の確認、認証失効やGuest期限切れ、重複端末・未送信キューの復旧、切替日をまたぐ遅延送信を先に解決する。端末から送られた時刻・価格を無条件に採用して過去売上を改変しない。PWA／IndexedDBとオフライン取込APIはPhase 2Aに含めない。

### Phase 2Bの試験UI・ローカル保存（本番デフォルト無効）

Phase 2Bでは上記の「将来」に記した範囲のうち、**一度開いたページの通信断への対応**だけを実装する。初回表示時にDatasetごとの有効レジ商品を取得し、標準18枚の元PNG（合計37,202,906 byte）ではなく、320pxのレジ専用WebP（合計194,886 byte）を必要に応じて読み込む。商品選択、±50個、金額・釣銭計算、返金への切替は端末内の素のJavaScriptで完結し、タッチごとのHTTPは発生させない。画像が欠損した場合は商品名の文字タイルへ代替する。旧商品登録・旧`/input`・Dashboardは変更しない。

会計開始時に生成したUUIDは同じ会計の再送に使い続ける。下書きはIndexedDBの`drafts`、確定操作後は`queue`へ入れ、両者の移動を1つのIndexedDB transactionで確定する。ローカル保存に失敗した場合はカートを残して「未保存」を表示する。保存に成功したときだけ次の会計に移る。`queue`は認証セッション由来のランダムなスコープとDataset IDで分離し、`pending`／`synced`／`needs_review`を保持する。同期済みでも端末の記録は直ちに消さない。別タブの同期はWeb Locks APIまたは短期IndexedDB leaseで直列化し、通信断では同じキーで指数的な待ち時間を置いて再送する。会計操作中はネットワークを待たない。ブラウザの保存領域の消去・端末故障まで復旧を保証するものではなく、Guest期限やログイン変更後の未同期会計を別Datasetへ移す機能もない。残る未同期・要確認の手動復旧手順は本番公開前に整備する。

サーバーの同期APIはCSRF、認証主体からのDataset解決、16 KiBの要求容量制限を通し、既存の`save_register_transaction()`を呼ぶ。サービスは**既存送信キーを先に照会**し、新規のみDBの商品行をロックして端末表示価格との差を調べる。価格が変わった場合はクライアント価格を採用せず409で停止し、元の会計記録を要確認として保持する。クライアント申告の営業日もサーバーのAsia/Tokyo当日と照合し、異なる場合は自動確定しない。同じキーの保存済み再送は価格や日付が変わっても保存結果を返す。端末時刻の真正性は証明していないため、過去営業日への正式取り込み、価格差額の処理、同期日時のDBカラム追加とお客様番号は後続Phaseの課題。

`REGISTER_V3_PREVIEW_ENABLED`と`REGISTER_V3_SAVE_ENABLED`はそれぞれ独立し、未設定では両方false。環境変数からの有効化は`LOCAL_DEVELOPMENT=true`のときだけ許す。テストは明示的にアプリ設定を切り替える。本番では画面もPOSTも閉じ、切替日行は投入しない。試験画面にも「本番の売上記録に使用できない」と明示し、保存フラグがfalseなら会計完了を無効にする。公開導線と旧入力停止は3A/3Bと切替工程のあとで扱う。

### Phase 2Cの例外表示・復旧境界

**実装済み**：会計は`drafts`から`queue`へ同一IndexedDB transactionで移す。下書き書込が一度失敗しても次の書込を試せるようにし、会計確定時にはqueueへの原子的な保存成功を確認する。`queue`の`submission_key`、表示単価、商品名、数量、端末の完了日時・営業日は書き換えない。`pending`は送信待ち／通信失敗後の再送待ち、送信中は画面のみ「同期しています」、正当なJSON応答でキー・金額・営業日・DB会計IDを確認したときだけ`synced`へ移る。`needs_review`（価格・営業日等）、`guest_expired`、`auth_required`は自動再送しない。認証確認が必要な記録だけは、**同じDataset・同じ認証セッションのスコープ**で新しいCSRFを得て画面を再取得できたときに、同じキーで再送を試みる。別セッションや別Guestへコピーしない。同期済みを含む記録はこの段階では自動削除しない。画面から離れている間はバックグラウンド同期を保証しない。

**営業日跨ぎ**：端末の日付が現在の東京日付と異なれば端末側で要確認として保持し、サーバーも自分の時刻と申告営業日を照合して409を返す。端末日時は証明されておらず、同じキーが既にDB保存済みかどうかを跨日で照会する専用APIもない。ゆえに要確認を勝手に削除・別日保存・別キー再送しない。将来の正式な過去日付取込には、認可された責任者による原記録と現金の確認、信頼できる時刻根拠（端末時計だけでは不足）、サーバー受信時刻と採用営業日・承認者・理由を残す監査記録、Dataset切替日と旧`DailySales`の排他検証が必要。会計の実日時／同期日時と承認監査をDBに表すmigrationの要否を別設計で決める。安全な根拠が成立するまで**過去日付への確定保存は未実装**。

**価格競合**：保存サービスは商品行ロック後のサーバー現行価格と端末の表示価格を比較する。差があれば該当商品名・表示単価・現行単価・1個当たりの差を409で返し、端末は同じキーの記録を要確認として保持する。この応答は照合結果であり、端末価格をDBの正本として採用する許可ではない。同じキーで既に保存済みなら従来どおり先に保存結果を返す。正式な解決候補は、価格改定の履歴・適用時刻または署名された商品価格版を確認し、権限を持つ責任者が受領現金と元記録を照合して承認または取消を監査付きで記録する方式。価格履歴・承認権限・差額処理がない現段階では自動調整／旧単価での強制確定は**未実装**。単価差×数量の会計差額も将来の確認画面で扱う。

**Guest期限切れ**：認証失効はAPIで`guest_expired`と区別し、ロック後の期限切れも同じ分類で拒否する。開いた画面では「利用期限が終了しました」と対象件数を表示し、元のIndexedDB記録を保持して再送を止める。別GuestやAdminのDatasetへ引き継がず、期限切れDatasetを復活させない。期限切れ後に画面を閉じると、既存認可では以前のスコープを再び閲覧できない。将来の回復方式は運用者の本人／端末／元Dataset確認、期限とcleanupの扱い、監査記録を別設計で決める。Guest Demoに本番売上の救済経路を暗黙に追加しない。ブラウザのサイトデータ削除、容量整理、端末故障、プライベートモード終了によってIndexedDB自体が失われる可能性は残る。端末保管だけで恒久的な記録保全を保証しない。

**Phase 3Aへの引継ぎ**：排他的な売上集計の入力はDBで確定した会計だけとし、`pending`／`needs_review`／`guest_expired`／`auth_required`を売上に数えない。元記録を管理者が照会・判定・監査し、送信済みか未送信かを安全に確認する手順、営業時間と過去日付の正式な取込、価格履歴、Guest期限切れの回復可否は未決定。本番の通常公開はこれらと3A/3Bの集計統合・切替検証が整うまで行わない。Phase 2CはDBテーブル・migration・本番切替行を追加しない。

## 4. 切替・互換性と集計

**最大の危険は旧日次行と新会計を同じ営業日について両方計上すること。** Datasetごとに`first_register_date`を一度記録し、`DailySales.date < first_register_date`と`register_transactions.business_date >= first_register_date`を排他的なデータ源にする。切替日は原則として翌営業日など**旧行が一件もない日**を選ぶ。既に当日の旧行があれば翌日へ延期する。既存の有効Guestが旧売上を持つ場合も同じ規則を適用するか、期限満了後の新規Guestだけを先に切り替える。過去にさかのぼる会計POSTや、切替日以降の旧`/input`へのPOSTをサーバーで遮断する。旧画面の表示停止だけでは不十分。デプロイ中の旧プロセスからの書込も想定し、切替前に実行中ワーカー・ルート・日付条件を運用確認する。段階的リリース時の二重書込を許さない。

既存`Product`と`DailySales`は移動・上書き・削除せず、旧日付の参照を続ける。独自品は同じDataset内の旧月次行から候補を提示し、店長が採用する行と現行価格を確認して新マスタへ**コピー**する。名前だけを使った自動統合や、旧Product IDの再利用はしない。標準18品はテンプレートの安定キーで一度だけ生成し、同名の旧行がある場合は候補・差額を表示して確認する。Phase 1BではGuestの新レジ独自品を**Dataset生涯30件**とし、`template_key IS NULL`の行だけを数える。標準18品と旧月次Productはこの新枠を消費せず、旧月次側の30件枠とも合算しない。

Phase 1Bの`register_products.py`は認可済みDatasetオブジェクトを受けるサービスで、HTTP routeは追加しない。`ensure_standard_products()`は`PRODUCT_IMAGE_OPTIONS`だけを読み、安定キーに対する`ON CONFLICT DO NOTHING`で不足品のみ挿入する。画像ファイルが欠けても商品は残し、画像キーをNULLにして後続UIで文字タイルへ代替する。既存行の名称・価格・画像・表示順・有効状態は更新しない。独自品の名前・価格の検証、Guest枠の判定、旧月次品の明示確認後コピーはサービス内で完結し、それぞれ成功時にcommit、例外時にrollbackする。PostgreSQLはDataset行のロック、SQLiteは同じ行への値を変えないUPDATEで書込を直列化する。将来のHTTPルートはフォームのDataset IDを受けず、認可済みDatasetを渡す。旧商品の無効行と500円超は暗黙にコピーせず拒否する。コピー確認UIと画像編集UIは後続Phaseで実装する。

移行前に、Dataset別・日付別の旧行数／数量／算出金額、ProductのNULL・同名異価格・画像キー・無効商品・当日旧行、既存の仕込み`product:<id>`を読み取り専用で棚卸しする。旧データには販売当時の単価がなく、現在の`Product.price`で計算した**旧仕様上の推計金額**しか復元できない。過去売上の価格不変性を遡及して保証したと表現しない。月次行の更新経路を止めた後は過去行の価格変更を禁止し、必要なら別の修正履歴を設計する。migrationでは導入前後の件数・識別子・合計とFK整合性を検証し、破壊的なdowngradeを許さない設計とする。

共通の売上読み取り層で、旧行（切替前）と新明細（切替日以降）を**各系統でDataset・営業日を絞って集約してから**足す。日別金額、商品別販売数（返金は負）、商品別金額、年月候補、ランキング、AI入力、ホームの今日の金額・「記録あり」、期間別APIをこの層へ順に切り替える。商品集計は安定商品IDを内部で使い、旧商品と新商品を同じ名前だからと機械的に結合しない。表示名が同じ別商品、改名、同日の価格違いをテストする。数量ランキングと売上金額ランキングは意味を分け、返金で負になることを表示する。

- 本日の差引売上＝対象営業日の旧金額（切替前のみ）＋新会計の`total_yen`（切替後のみ）。商品別数・金額も同じ排他条件。会計件数は新会計ヘッダーの件数（返金を含む）。平均＝**新会計の差引金額合計 ÷ 新会計件数**。表示用の丸め方は実装時に固定する。
- 旧データだけの日は会計件数も平均も「記録なし／算出不可」と表示し、0件・0円と混同しない。旧新が混在する期間では、**全期間売上**と、明示した**レジ導入後のみの会計件数・平均**を別ラベルで示す。全期間売上を新会計件数で割らない。
- 前日比と先週同曜日比は、各営業日の差引売上を同じ排他規則で比較。比較対象に記録がない場合と0円を区別し、0円を分母にした変化率は表示しない。`sales_period_summary.py`の週の起点・進行期間の比較日数・うるう年処理は維持する。
- Guestが会計後に`/dashboard`へ戻れば自分のDatasetのみが見える。AI分析も同じ正本の集計を使い、GuestのAI回数制限を維持する。返金を含む数量・負数をプロンプトへ渡す形式は別途テストする。

### Phase 3Aの読み取り契約（実装済み、公開画面への接続は3B）

`register_sales_aggregation.py`は認可済みの`Dataset`オブジェクトと営業日の両端を受ける。HTTPでは引き続き`require_current_dataset()`でDatasetを決め、外部からDataset IDを選ばせない。サービスもDatasetの存在とGuestの期限を確認する。`aggregate_sales(dataset, start, end)`は両端を含む範囲、`aggregate_period(dataset, period, offset, today)`は既存`period_bounds()`の暦と進行中期間の同じ経過日数を用いた前期間比較、`sales_year_months(dataset, start, end)`は記録のある年・年月を返す。参照のみで既存データ・切替日を変更しない。

- 切替未設定では旧`DailySales`だけ、設定済みでは切替日前の旧行と切替日以降の確定済み`RegisterTransaction`だけを読む。ローカル未同期・要確認はDBに確定していないため数えない。対象範囲に切替日以降の旧行、切替日前の新会計、または切替未設定で新会計を検出したら`SalesCutoverIntegrityError`（違反行数付き）を送出し、正常な集計値として隠さない。検出対象は要求した営業日範囲であり、運用開始前には全期間の棚卸しが別途必要。
- 日別と商品別の金額が一致しなければ`SalesAggregationConsistencyError`を送出する。DBのヘッダーと明細には合計一致の横断制約がなく、破損または複数クエリ間の同時更新があり得るため、食い違う結果を表示しない。PostgreSQLの通常の`READ COMMITTED`では複数SELECTの完全な同一スナップショットは保証されない。Phase 3Bの公開接続前に、読取トランザクションのスナップショット固定または一貫した再試行方法を検討する。切替違反の検査は対象範囲で集計の前後に行う。
- 返却値は整数円の`total_yen`、`legacy_total_yen`、`register_total_yen`、`has_record`、記録がある日だけの`days`、系統付きキー（`legacy:<Product.id>`／`register:<RegisterProduct.id>`）の`products`、レジ会計の`transaction_count`、`sale_count`、`refund_count`、`average_yen`、`average_display_yen`など。`days`が空なら未記録、0円の行があれば`has_record=True`。会計ヘッダーの金額と件数は明細をJOINせず集計し、商品別数・金額は明細スナップショットを使う。レジ商品はIDで集約し、改名前後の名称別内訳を`snapshots`に残す。旧商品の金額は従来どおり現在の`Product.price`による推計値。
- `transaction_count=None`は対象範囲が旧売上のみ、または切替未設定であり、会計件数を算出できないことを表す。切替日以降を含む期間では実際の新会計件数を整数で返す（未記録なら0件）。旧新混在期間も平均の分子は`register_total_yen`だけで、返金を含む新会計件数で割る。会計が0件なら平均は`None`、それ以外は整数の分子・分母から`Decimal`で除算して保持し、画面表示用だけ1円単位の四捨五入（`ROUND_HALF_UP`）を使う。循環小数は`Decimal`の演算精度に従う。商品別数量と金額は返金分を負数で集計する。
- 前期間に記録がなければ`previous_yen=None`、記録があって差引0円なら`previous_yen=0`。`difference_yen`は比較対象に記録があるときだけ計算し、変化率は比較対象が正の金額のときだけ算出する。0円・負数は分母にせず`comparison_rate_percent=None`。変化率は`Decimal`で計算し小数第1位へ四捨五入する。日・週・月・年の比較対象範囲は既存APIの規則に合わせる。

Phase 3Bでは`app.py`の`_get_today_sales_amount()`、`_has_today_sales_record()`、`_get_sales_from_db()`、`_get_dashboard_sales_months()`、`_get_dashboard_sales_years()`と、`dashboard()`、`api_dashboard_data()`、`api_sales_period_summary()`、`api_ai_advice()`、`home()`の呼び出し・表示契約を確認して段階的に切り替える。既存`/api/sales-period-summary`の返却形は3Aでは変更しない。日別推移・商品ランキング・比較対象の未記録表示・AI入力を新契約へ写すアダプターを3Bでテストする。切替後の旧`/input`書き込み停止と本番切替日は別工程で検証し、切替条件違反の運用表示または警報も公開接続前に決める。新集計を追加しただけでは本番公開は可能にならない。

### Phase 3Bの試験接続と公開前の条件

`REGISTER_V3_AGGREGATION_ENABLED`はレジのプレビュー・保存とは独立し、通常環境の既定は無効。テストまたは明示的なローカル開発時だけ統合集計を使い、OFF時の公開画面・JSON・AIの従来契約を維持する。ON時は`register_sales_view.py`が3Aの結果を`dashboard()`、`api_dashboard_data()`、`api_sales_period_summary()`、`api_ai_advice()`、`home()`へ変換する。既存APIの`total_sales`、`previous_sales`、`difference`、`comparison_rate`、`chart_labels`、`chart_values`、`rankings`と`ranked_sales`配列形を維持し、会計件数・平均・記録の有無・商品キーを追加する。旧系統と新系統の同名商品はID付きの補助表示で区別する。旧売上の正確な会計件数は引き続き算出しない。期間APIの`previous_sales=None`は比較対象に記録がないことを示す。0円と未記録は`has_record`で区別する。AIには識別表示、差引数量、差引金額を渡し、返金の負数と旧単価が推計であることを明示する。Guestの既存AI回数制限を維持する。

PostgreSQLでは通常の認証・SessionがSELECTを開始した後に分離レベルを変更できないため、集計要求に専用接続を開き、`REPEATABLE READ`・`SET TRANSACTION READ ONLY`のトランザクション内でDataset確認、切替確認、日別・商品別、比較期間と候補年月を読み切る。通常の会計保存に行ロックを要求せず、読取後すぐ接続を解放する。SQLiteの通常pytestでは既存sessionを使い、金額照合によって矛盾を検知する。隔離PostgreSQLで会計保存と同時に読み、同一読取要求は旧スナップショットを保ち、次の要求は確定した会計を読むことを検証する。

ON時の切替違反／金額不一致は安全な503画面または`{"error":"sales_integrity_error","incident_id":"…"}`の503 JSONとし、売上数値を返さない。画面更新の失敗時には既に表示されていた期間の数値とグラフを消し、古い数字を新しい選択結果として見せない。ログはエラー型、処理名、Dataset UUIDの短いハッシュ、対象期間、切替違反件数、調査用IDに限る。SQLや秘密情報を利用者へ出さない。

旧`/input`のPOSTは商品・数量検証後、同一DB transaction内でDataset行をロックし、`RegisterCutover.first_register_date`以降を409で拒否する。GETの案内は補助でありPOSTを防ぐ根拠ではない。管理者デモ投入スクリプトも同じロックと日付規則を使う。切替未設定と切替前の旧日の修正は従来の上書きを許すが、旧単価の履歴制約があるため監査記録付きの訂正手順は本番切替前に決める。**将来の切替日設定処理は同じDataset行を先にロック**し、既存旧行を調べてから設定する必要がある。現時点では本番切替日を設定するHTTP経路はなく、このロック規約を守らない外部DB操作まではアプリで防げない。

本番導入前には全期間の違反行棚卸し、切替日前後の旧／新経路の停止確認、切替日を設定する管理手順、デプロイ中の旧アプリワーカー停止または全ワーカー更新の確認が必要。旧版ワーカーは今回の`/input`ガードを持たないため、切替日を投入する前に旧版プロセスが一つもPOSTを受けないことを運用で確認する。端末未同期記録の過去日付取込・価格競合・Guest期限切れ復旧も未解決であり、PRのマージだけで本番レジは利用可能にならない。

### Phase 4Aの商品管理（試験環境のみ）

`/register/products`は独立した`REGISTER_V3_PRODUCTS_PREVIEW_ENABLED`で閲覧し、書込にはさらに`REGISTER_V3_PRODUCTS_WRITE_ENABLED`を要求する。両者の通常環境既定値は無効で、テストまたは明示的なローカル開発環境のみ許可する。レジ画面のプレビュー・保存・集計フラグと連動させず、旧月次商品画面を残す。GET時に認可済みDatasetの不足する標準18商品だけを作成し、既存の価格・名前・画像キー・並び・販売状態を初期化しない。独自商品は名前1〜100文字、整数0〜500円、画像なしで作成する。0円の商品を登録できることと、暫定的に0円会計を拒否することは別の規則である。Guestの独自品30件は旧月次枠および標準18品から独立し、Dataset行ロック下で数える。

編集はDatasetで絞った商品IDに対し、署名付きの元の名前・価格と現行値を比較する。同一フォームの再送は安全に扱い、別画面で変更済みの値を上書きしない。レジは次のGETから更新値を取得し、開いたままの古い単価は会計保存時のサーバー照合で409とする。既存カート・未同期記録と、過去会計の商品名・単価・合計スナップショットを変更しない。

旧`Product`からのコピーは所属Dataset・販売中・単価500円以下を確認し、署名付きで提示した名前・価格が現在も一致し、利用者が確認欄を選んだ場合だけ、別の`RegisterProduct`を作る。同名を統合しない。旧商品・`DailySales`・仕込みレシピキーは変更しない。新規登録と旧商品コピーには会計キーとは独立したUUID送信キーと内容のdigestを使用する。`register_products`にnullableの`creation_key`・`creation_digest`を追加し、`(dataset_id, creation_key)`の一意索引を最終防壁とするmigration `a4e8c2f6d901`が必要。旧行はNULLのままでUPDATEせず、標準品もキーを使わない。同じキーと同じ入力は保存済み商品を返し、異なる入力は409。Dataset行ロックでGuest上限と二重POSTを直列化する。新migrationのdowngradeはSQLiteの部分削除を避けるため、レジ4表のいずれかに行があれば先に拒否する。

画像は既存の安全なキーとWebPを参照し、欠損時は文字タイルにする。画像選択・アップロードの見かけだけのボタンは設置せず、未対応と明示する。Admin向け画像カタログ申請とGitHub PR投稿経路を変更しない。**Phase 4B**で承認済み画像の選択UIと仕込み管理への参考連携を検討する。Phase 4Aでは本番切替日、会計保存経路、旧月次商品画面、Dashboardを変更しない。

仕込みとの最小連携は、販売個数を**参考値**として仕込み画面へDataset・商品キー・営業日付きで渡す読み取り導線。`PrepRecipe`と`PrepPlan`を勝手に更新せず、必要なら店長が予定数に反映する。返品・廃棄・製造ロスを含まないため販売数を実際の材料消費量や在庫変化とは呼ばない。`template:<key>`は新マスタの標準キーへ対応付けられるが、`product:<旧ID>`は移行時に対応を確認し、レシピの参照先を自動で変更しない。材料発注メモへの既存導線は維持する。GuestにAdmin専用の仕込み画面を公開しない。

### Phase 4Bの画像と仕込み参考表示（試験環境のみ）

レジ商品管理の画像ギャラリーは`REGISTER_V3_PRODUCTS_PREVIEW_ENABLED`、選択POSTはさらに`REGISTER_V3_PRODUCTS_WRITE_ENABLED`で保護する。認証済みDatasetの商品IDだけを対象にし、署名付きの元の商品名・価格・画像キーをDataset行ロック後の値と照合する。再送で同じ画像を選ぶ場合は冪等に成功する。画像キーはサーバー側で`available_product_image_assets()`から再評価し、Guest非公開・欠損・カタログ外を拒否する。`RegisterProduct.image_key`だけを更新し、商品ID・標準`template_key`・商品名・価格・会計明細は変更しない。画像なしの選択はNULL。標準18枚はレジ専用の軽量WebP、承認済みAdmin画像は既存の最大500KiBのWebPを使用し、候補を遅延読み込みする。ファイル消失時のレジは文字タイルを維持する。Admin画像の申請・PR経路、新規アップロードは変更・追加しない。

Admin専用の`/prep`と`/prep/plans`の参考表示は既存の`REGISTER_V3_AGGREGATION_ENABLED`が明示的に有効で、かつテストまたはローカル開発環境の場合だけ表示する。本番既定値では表示しない。`sales_read_snapshot()`内で対象Dataset・営業日について`aggregate_sales()`を読み、同じスナップショットで標準`template_key`をレジ商品IDに解決する。切替日前は`product:<旧Product ID>`を旧商品IDに、切替日以降は`template:<key>`を新レジの標準商品IDにだけ対応させる。同名でも旧・新・独自商品は合算しない。商品別の正味数量は返金分を差し引き、確定済みDB会計だけを対象とする。営業日の売上記録がなければ「未記録」、記録があり対応商品が売れていなければ「0個」と表示する。未対応の独自レジ商品の販売実績は商品ID付きの折りたたみ欄で区別する。集計違反は既存の安全な503エラー処理へ渡し、部分的な正常値を表示しない。販売実績の取得は読取専用であり、製造予定、レシピ、材料試算、在庫、発注を更新しない。

Phase 5への課題：独自レジ商品とレシピの恒久的な紐付けにはDatasetを含む明示的な商品ID対応、外部キー、移行時の同名商品確認が必要。今回の名前による推測をしない方式のまま設計する。本番切替日前には切替行と旧入力停止、全デプロイワーカー、未同期会計、価格・営業日競合、画像カタログの公開設定と実端末の表示負荷を検証する。

## 5. Dataset・権限・画像の境界

- レジ閲覧・POSTは`admin_or_guest_required`と`require_current_dataset()`を使い、Dataset IDをフォーム・URLで選ばせない。商品・会計・明細・集計のすべてをDatasetで絞る。複合FKで他Datasetの商品を他会計に挿せないようにする。Guest A/BとAdminの相互参照・更新・削除をテストする。
- Guestの会計件数・明細数・1POST行数・1商品数量・預かり金額／合計、独自商品数、リクエスト容量に上限を置く。具体値はアクセス負荷を見て決定し、並行POSTでも上限を越えないようDatasetロックとDB制約を組み合わせる。期限切れ判定は書込ロック取得後にも再確認し、cleanupは対象Guestの明細→会計→新商品→旧売上→旧商品→Datasetを削除。管理者と有効Guestは対象にしない。cleanupと会計POSTの競合をPostgreSQLでも検証する。
- `CSRFProtect(app)`を新しいフォーム／JSON POSTにも適用し、XSSはテンプレートの自動エスケープを維持。サーバーが価格、数量、商品の有効性、返金区分、合計、お釣りを再検証する。返金承認や直接数量入力はJSだけで成立させない。
- 将来の実店舗販売員は、独立した認証主体と`register:read/write`権限に限定する。レジ専用のendpointをサーバー側の許可リストで検査し、管理URL、API、静的なデータ公開経路を含めて認可する。各リクエストのDatasetも認証主体に固定する。単なる「戻る」非表示や店長／販売員UIモードでは保護できない。今回のAdmin/Guest共通体験にはこの実店舗ログインを混ぜない。
- 画像のある標準品は既存の安全な画像キー解決を利用する。独自品は名前・価格のみで保存でき、画像未設定なら文字タイル。商品一覧に編集ボタンと承認済みテンプレートギャラリーを段階追加する。未実装の「画像を追加」はdisabledにして体験版では未対応と明記し、POST先や疑似アップロードは作らない。Adminの画像カタログ投稿→PR→承認→デプロイの経路は独立機能として維持し、店舗内の商品編集と区別する。

## Phase 5A：RenderでのAdmin専用レジ操作デモ

`GET /register/demo`は`REGISTER_V3_PUBLIC_DEMO_ENABLED=true`かつAdmin認証時のみ表示する。未設定・falseなら404、Guestは403、未認証者はログインへ案内する。フラグは`LOCAL_DEVELOPMENT`から独立し、未設定時はfalse。セッションCookieのSecure属性、既存のプレビュー・保存・商品管理・集計の各フラグを変更しない。Admin向けサイドメニューにもフラグONの間だけ「レジ操作デモ（未保存）」を表示する。

表示する18品は`register_products._standard_rows()`の標準定義と承認済みの軽量WebPからリクエスト中に組み立てる。DBからDatasetや`RegisterProduct`を読まず、`ensure_standard_products()`も呼ばない。欠損画像は文字タイルで表示する。価格は練習用の標準初期値であり、実店舗の商品マスタの変更後の価格とは連動しない。

デモHTMLは正式プレビューと商品タイル・会計欄を共用するが、ロードするスクリプトは`register_demo.js`だけにする。共通の`register_core.js`で数量、販売・返金の分離、合計、預かり、お釣りを計算する。専用JSには`fetch`、IndexedDB、sessionStorage、保存APIのURL、送信キーを持たせず、状態はその画面のメモリ内だけ。疑似完了後は「練習会計が完了しました。この会計は保存されていません。」と表示し、次の練習で入力を破棄する。DB会計、明細、商品、切替、旧日次売上、仕込み予定・レシピ・材料には触れず、実際の会計番号や売上履歴は作らない。保存APIは従来どおりプレビューと保存の両フラグを要求する。

### Renderでの有効化・無効化手順（このPRでは未実施）

1. PRをレビューし、関連テストとCI、mainへのマージを確認する。通常のデプロイが完了してから、既存Adminでログインできること、旧売上・ホーム・Guest Demoが維持されていることを確認する。

3. Adminで`/register/demo`とナビ導線を開き、練習会計と未保存表示を確認する。未認証・Guestでは利用できないこと、正式会計APIが閉じていること、既存の売上件数が変わらないことを確認する。ブラウザの通信・ストレージ画面で会計POSTとIndexedDB書込がないことを確認する。
4. 無効化するときは同じ環境変数を`false`にするか削除し、再デプロイ後にデモURLが404、ナビ導線が消えたことを確認する。コード自体を戻す必要があれば、別PRで差分をrevertする。練習データの削除やDB migrationは不要。

## Phase 5B：正式切替前の監査と復旧準備（本番切替は未実施）

### 読取専用の切替監査

`REGISTER_V3_READINESS_ENABLED`は未設定時falseで、正式プレビュー・保存・集計・商品管理・Adminデモから独立する。migrationを適用した環境で明示的に有効化した場合だけ、Adminが`/register/readiness`を開ける。認証主体のDataset以外は指定できない。画面は`sales_read_snapshot()`（PostgreSQLではread only / repeatable read）内の`audit_cutover()`で、旧Product・DailySalesと営業日範囲、RegisterProduct、確定済み会計・明細・RegisterCutover、旧新の同日重複、境界前後の不正記録、ヘッダーと明細の合計、標準品の不足・無効、有償品の有無、500円を超える旧商品、レシピ対応がない旧商品・独自商品を確認する。0円商品は登録できるが、0円だけの会計は保存サービスが拒否する。同名の商品はIDで区別し、旧商品を暗黙に新マスタへコピーしない。登録済みの価格はデモの初期価格とは無関係で、過去会計の単価・名前・合計は明細のスナップショットとして不変。

判定は「切替不可」（重複、日付境界違反、会計・明細不一致、切替日なしの新会計、既存切替日との矛盾、新規予定日の過去日指定）、「確認が必要」（商品不足・無効、有償商品なし、500円超やレシピ未対応、予定日未指定）、「DB上の切替条件を満たす」の3種と理由を返す。予定日は厳密なYYYY-MM-DDの暦日として受け取り、Asia/Tokyoの営業日の日付列と比較する。入力・GET・監査で切替行、商品、売上、レシピを作成・更新・削除しない。判定はその時点のスナップショットであり、ブラウザのIndexedDB内の未同期会計や全端末数を推定できない。

### 最終切替時の排他規約（Phase 5Cの実装条件）

本PRに切替日設定APIは含めない。将来の設定処理は`_lock_dataset()`で対象Dataset行を`SELECT ... FOR UPDATE`してから、同じトランザクション内で旧DailySalesの予定日以降・新RegisterTransactionの予定日前・既存切替行・監査エラーを再検査し、承認した日だけRegisterCutoverを設定してcommitする。旧`/input`のPOSTは`assert_legacy_sales_writable()`で、新会計保存は`save_register_transaction()`で同じDataset行を先にロックする。これにより待機した旧POSTは切替commit後の境界を見て拒否され、先行した旧POSTがある場合は切替側の再検査が拒否する。GETの監査結果のみを条件に切替行を確定してはいけない。PostgreSQLの実並行テストは既存`test_cutover_lock_serializes_legacy_writer`を維持する。正式切替には店長の明示承認、端末内キュー・バックアップ・本番データの再確認が必要。

### 未同期会計の保存状況

正式レジの`GET /api/register/transactions/<submission_key>/status`はプレビューと保存の両フラグを要求し、認証済みDatasetだけを検索する。GETは新規保存しない。確定済みなら会計キー、ID、営業日、種別、合計、お預かり、商品ID・数量と会計時の単価を返し、別Datasetまたは未発見なら`not_found`を返す。端末側の手動「保存状況を確認」は既存Web Locksまたは同一scopeのリースで自動同期と競合しない。同じ送信キーと全明細・単価・金額が一致した会計だけ`synced`とし、違いは`needs_review`と理由を保持する。`not_found`や通信失敗は「未保存の証明」ではなく`pending`のまま。照会はキューを削除せず、新キーも発行せず、異なるDatasetへ移さない。デモはこのAPI、IndexedDB、正式レジのJSを使用しない。

### Phase 5C追加：未同期会計の永続保全と監査

### Phase 5C最終追加：期限付き端末準備と翌営業日の自動同期

端末への会計記録が成功した時点で会計完了と表示し、カートを空にして次のお客さんへ進む。サーバー確定とは別表示。通信復旧後、`/api/register/offline/session` でAdmin認証・Dataset・端末許可を再検証してCSRFを再取得する。個々の元キーをstatus GETで照合し、完全一致なら再保存せず同期済み、未発見なら同じキー・元明細・許可トークンで `/api/register/offline/sync` にPOSTする。保存後もstatus GETで一致するまで同期済みにしない。応答不明ならpendingで元記録を保持する。別タブは既存のWeb Locks/IndexedDB leaseで排他し、50件中の一部失敗でも正常分を順番に確定する。サーバーでは通常POSTと例外復旧POSTとは異なる受入経路にし、Dataset行ロック、既存キー・復旧案件再照合、署名版・営業日・期限・商品ID・金額・旧DailySales・切替日を検証する。商品価格が更新済みでも、事前承認版の名称・単価が一致すれば元の価格で確定する。競合・期限超過・証拠不一致は自動確定せず要確認にし、必要なら既存の復旧案件へ保全する。未確定キューはDashboard・ホーム・AI・仕込みの確定売上に加えない。

ログアウトは全端末許可をサーバーで失効させ、ブラウザにもローカルのロック印を残す。紛失時はAdminがオンラインでログアウトして許可を失効させ、会計控え・現金日報と全端末を照合する。オフライン中の権限取消は即時には伝わらず、端末時計の変更やブラウザプロフィールを占有した相手に対する期限の完全保証もない。PINとブラウザプロファイルを守り、共有端末にはOS側のロックを使う。IndexedDB消去・破損、完全な端末故障、ストレージ書込失敗で未送信の会計を自動復元できない。書込失敗時は入力を保持して会計完了を停止する。保留・復旧案件は管理者が控え、現金日報、価格履歴を調査し、根拠不足なら引き続き保留する。

**本番公開判定は保留。** コードと単体テストだけではスマホ・横向きタブレットの実再起動、通信断・ストレージ障害、全端末点検、現金照合、本番バックアップ・復元、隔離PostgreSQL並行試験を確認したことにならない。これらをPhase 5D前に実施し、未確認端末や未解決会計があれば停止する。フラグは既定falseで、PRのmergeだけでは正式公開されない。Guest Demo、Admin非保存デモ、旧日次入力は維持する。

### Phase 5Dの手順と停止条件（Phase 5C当時の記録）

### Phase 5C 実ブラウザE2E検証（Draft PR #120）

`tests_e2e/server.py` は一時SQLiteへ専用Admin Dataset、商品、テスト用切替日を作り、ランダムなテスト認証情報とlocalhost限定の検査用経路を用意する。認証CookieのSecure属性だけをHTTPのlocalhost用に無効化し、正式機能のフラグは**この隔離プロセスだけ**で有効化する。CIの`register-browser-e2e`はChromiumとPlaywrightを導入してこのサーバーを起動する。検査経路は本番アプリには登録されず、本番DB、Render、実売上には接続しない。ローカル実行は`python -m playwright`ではなく、アプリディレクトリで`npx playwright test --config=tests_e2e/playwright.config.cjs`を使う。Python環境が別の場合は`E2E_PYTHON`で指定する。

ブラウザ試験は、オンラインAdminログイン、明示的な翌日承認、PINによる端末準備、Service Workerのscopeと専用シェルのキャッシュ、誤PINの拒否、通信断の販売・返金、3件後の再読み込み、同一プロファイルでのブラウザ終了・再起動、5件の元キーとキューの保持を確認する。サーバー時計は隔離環境内だけ翌日に進め、商品価格を120円から140円へ変更してから通信を復旧する。1件の保存成功後にHTTP応答だけを失わせ、元の営業日・120円・明細が5件とも一度だけ確定し、キューが消えないことを検証する。スマートフォン相当と横向きタブレット相当のChromium画面サイズも試す。別の端末許可で101件を端末に記録し、100件を同期、101件目を要確認として保持する。IndexedDB書込失敗を注入し、カートが消えず会計完了とならないことを確認する。

2026-10-17のGitHub Actions（Ubuntu 24.04、Playwright 1.62.1、ヘッドレスChromium、一時SQLite）では、上記の**6シナリオがすべて成功**した。スマートフォン相当は390×664、横向きタブレット相当は1024×768の仮想画面とタッチ入力で確認した。Service Workerのオフライン起動、PIN誤入力時の非表示、連続した販売・返金、再読み込み・同一プロファイルのブラウザ再起動、応答喪失後の同一キー照合、翌営業日・価格改定後の元日付と元価格への同期、100件成功と101件目の要確認、書込失敗時の入力保持、Adminログアウト後にキャッシュ済みシェルからPINで会計を再開できないことをブラウザ上で確認した。これは実機試験の代わりではない。
同じ候補のCIでは全pytestが1329 passed、44 skipped、JavaScriptが30件成功、隔離PostgreSQLのmigration・制約23件と追加並行処理20件が成功した。新しいmigrationは追加していない。

ブラウザを完全に終了した後、AdminのセッションCookieが失われた場合は、自動同期を開始しない。未同期5件を残して再ログインを案内し、オンラインでAdminが再ログインして同じ端末をPIN解除すると、個別承認なしで5件を照合・同期した。端末許可の失効は再準備の案内と区別する。認証が失効したまま売上へ反映されることを許さない。

36時間の端末許可、満了後48時間の同期猶予、1会計50,000円の境界や許可失効・別Dataset・Guest拒否はサーバー側の対象pytestで検証する。ブラウザE2Eで実行した件数境界は100件／101件であり、他の境界をブラウザで検証済みとは扱わない。保存容量不足はIndexedDBの書込例外を注入して再現したもので、実際のOSストレージ枯渇やDB破損は未確認。Service Worker更新途中の障害、複数タブ、端末時計の改変、実機のログアウト後キャッシュ確認も別途検証が必要。

これらは**Chromiumの仮想画面と使い捨てブラウザプロファイル**の検証である。実スマートフォンの電源再起動、OSの保存領域不足・破損、タブレットのタッチ感、通信機器の実障害、ブラウザデータ消去からの復旧を検証済みとは扱わない。IndexedDB自体が消え、外部記録のない会計は自動復元できない。100件を超えて端末へ記録できても、同じ許可では101件目を自動売上確定しない。店長は元記録・控え・現金日報を保全し、既存の復旧案件として根拠を調べ、次の販売継続に必要な新しい端末許可はオンラインで別途準備する。会計キーや営業日・価格を付け替えて再送しない。

Phase 5D前には、隔離された検証環境を使い、スマートフォンで端末準備、PIN、写真タッチ、販売・返金、通信断の再読み込み・ブラウザ終了・端末再起動、復旧後同期を順に確認する。横向きタブレットでは商品一覧、数量、預かり入力、未同期件数、PIN解除と再起動後の復帰を確認する。各端末の元キー・端末件数・サーバー確定件数・営業日・金額を照合し、未確認の端末と未解決案件があれば本番切替を止める。本番バックアップ復元、本番DB監査、価格確認も従来の停止条件のまま。
